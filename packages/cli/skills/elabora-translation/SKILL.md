## Translating a course
One package per language; the translations stay in the source course.
1. Read `elabora_translation_table { language: "de" }` (`screen` narrows it; `todo: true` lists work left). No export is needed to start a language. For an external translator, `elabora translate export . --to de` creates or updates `translations/de.xlf` (XLIFF 2.0).
2. Write `elabora_translate_text { language: "de", texts: [{ unit, target }] }`: a batch is one validated, undoable change, and starts the language automatically. Keep Markdown, `$…$` maths (decimal commas inside maths as `2{,}5`), links, code and placeholders; place narration word markers on the corresponding translated words. Alternatively edit XLIFF targets and mark segments `state="translated"`. The app shows the same texts in « Traduction » and in context.
3. Check `elabora_translation_status { language: "de" }` (`elabora translate status . --to de --json`) until `ready`: no missing, stale or broken texts or unplaced word anchors. Plan approval is separate. See `elabora_look { language: "de", screen }` while translating.
4. From the **source course's same server**, use `elabora_validate`, `elabora_check_fit`, `elabora_preview_screenshot`, `elabora_build` and `elabora_test_package` with `language: "de"`. Builds write the translated package and proof into the source's `dist/`; no server switch or generated-folder editing. `allowMissing: true` on checks/build/test explicitly permits a draft (source text for missing/stale units; unplaced word anchors at line starts). Fix translation or design in the source. `release: true` requires the author's approval of the translated plan (step 5). The convenient CLI alternative is `elabora translate build . --to de --out ../<course>-de --json`, then validate, fit, screenshot, build and test that copy.
5. The author approves the translated plan; you carry it out with their yes, as before a paid generation. `elabora_translation_approve { language: "de" }` writes nothing and returns `ask`: what to put to the author (the plan, its texts translated, the name the approval shows). Ask them in their language, in a sentence; only once they said yes, call again with `authorApproved` (the `contentHash` it gave) and `by` if it was `null`. Never approve on your own or from an earlier yes: a plan changed since is asked again. Without MCP: `elabora translate approve . --to de` (exit code 3 and the question), then `--author-approved <contentHash>`. A client's approval is the author's to record in Elabora (Traduction). Source changes make affected units stale; their previous translation is kept for review. Every tool above also works through `elabora tools call <tool> . --args '<json>'` without MCP.
