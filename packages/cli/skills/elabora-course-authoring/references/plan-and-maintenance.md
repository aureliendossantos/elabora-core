# Planning, plan revisions and maintenance (on demand)

**Read the course, write the plan.** `elabora_overview` (or `elabora project .`) and `elabora_get_plan`. The author's sources (the client's brief, decks, recorded interviews) are in `sources/`, never published: list them with `elabora_sources` and read each through its readable version, `elabora_source_read` (`elabora sources read . <file>`: Markdown made on this computer with a document's comments and tracked changes, a deck's slides in reading order with their notes and pictures, a recording's transcript), not by opening the .docx or .pptx yourself; they may hold personal data, so quote only what the module needs. A plan with no version yet (`versions.latest: null`; a new course's plan is a placeholder) is yours to draft before any screen: from the author's request, the files in `sources/`, their choices (« Notes for this course » in `AGENTS.md`; `audience`, `businessGoal` and `duration` already in the plan) and objectives, write it whole with `elabora_write_plan { plan }` (or patch it: `{ patch }`; `elabora plan write . --from plan.json`), observable objectives (skill `elabora-pedagogy`) each with a `short` name of three to five words, items in order with their kind and their `part` (the module's parts, by title: the sections you will make), locked texts only where the client must see the exact words; then ask the author to read it, make its first version and send it to their client (Plan › Versions, « Créer la V1 », then « Exporter »). A vague request still gets a whole plan at once, never a questionnaire first: decide what the author left to you (the request says it) and say it in the plan, where the app shows it first: `decided`, one entry per decision (`topic`: `3d`, `tone`, `format`, `quizzes`, `case`, `brand`, `voices`, `duration`… or another with a `label`; `choice` in a few words; `why`: where it shows, « partie 3 »; `items`), and `question`, the one question whose answer would change the plan most (`text`, `items`), only when you cannot decide it well yourself. One question at a time: when the author answers (a new request), update the plan, then ask the next one or remove `question`. Validating a version removes both: they are never part of the contract, and nothing a reviewer reads names you as its author. Never make a version, never record a validation: the author does. After a validation you still write the plan, and the changes show as changes since the validated version.

## When the plan seems wrong
Correct it with `elabora_write_plan`, whether a version of it was validated or not, and tell the author what changed and why (source, guardrail): the app marks each change since the validated version, `elabora_plan_diff` lists them, and the author decides whether the next version keeps them, writes a note for the client on each, or goes back to the validated wording. A change of substance (what is taught, a rule, an answer) is the author's call: ask before you write it. Moving items (a `move` in the patch, or another `part`) moves their screens in the same change. Never change a text kept « à l'identique » (`verbatim`): Elabora refuses it; ask the author. When the author wants to send the plan to their client, `elabora_export_plan_document` writes it in `dist/` (`docx` for a client who comments in Word, with the changes since the validated version as tracked changes; `pdf` to sign): it shows the latest version and never makes one, so when the plan changed since, tell the author, who makes the next version first or sends this one.

## Ids
Lowercase-hyphen ids, unique in the whole course, prefixed by the screen id (`evaluation-q1`). Ids are permanent: learner progress is keyed by id. To rename one, use `elabora rename . <old> <new>` (MCP `elabora_rename`), never a file edit: every reference, the screen file and `elabora.lock.json` follow, so learners keep their progress. Ids written in free-object code or generators are yours to update. A variable is renamed with `elabora_rename_variable` (the events that use it and learners' saved values follow).

To change a word everywhere learners read it (a name, a term the client changed), `elabora_find_text` shows where it is and `elabora_replace_text` replaces it in one undoable change; validated texts of the plan are not touched: they are the plan's, written with `elabora_write_plan`.

## Format version
`course.json` `format` is `elabora/0.1`. A course in an older format still validates and builds (`I_FORMAT_OUTDATED` lists what changes); `elabora migrate .` writes the migration as one change after a backup (`elabora undo` reverts it), and the first edit through Elabora does it too. `E_FORMAT_NEWER`: the course needs a newer Elabora; do not edit it.
