# Engine

The editing session of the desktop app: the project in memory, one write queue, incremental validation, other writers, batches, media jobs and the message protocol. Part of the [architecture](../architecture.md), the contract every change follows.

`@elabora/engine` keeps one project in memory for the desktop app: `openProject(dir, options)` returns a `Session` holding the files snapshot (what the journal knows of the folder), the project loaded from it, a validation context, the findings per screen and of the project checks, the journal's entries and the open AI batch. Files on disk stay the source of truth: agents keep editing them through the `elabora` command, the MCP server or their own file tools. The session owns the write queue and project state; `base/canvas.ts` owns the canvas's state, given a sink (the desktop's local host), and `session-voice.ts` owns voice, alignment and transcription jobs; `session-monitor.ts` owns watcher observation and retry scheduling. Journal transactions and reconciliation stay in the session. Their writes go through the session's queue.

## The base without Node
What a session needs and Node does not give is under `src/base/` ([D100](../decisions/D100.md)): files that import neither `node:` modules nor `@elabora/node`, checked without Node's types (`packages/engine/src/base/tsconfig.json`) and bundled for a browser by esbuild, which fails at an import of Node (`test/unit/browser-base.test.ts`), for the desktop's session and a browser engine alike. It holds:
- **the state and the reads**: the project in memory and its incremental validation (`base/project-state.ts`), the renders' memory (`base/render.ts`), the write queue (`base/queue.ts`), the errors of the protocol (`base/errors.ts`: a host adds its own, the desktop's lock and journal in `errors.ts`), and the requests that only read the project (`base/reads.ts`, `SessionReads`: the summary, files, screens and their parts, findings, a timeline and its moments, effects, the plan's versions, diff and document, a dialogue and its paths, texts, conversions and languages, the format, a screen rendered, the history). The renders' memory is the session's: the canvas service (`base/canvas.ts`) is given it, so that rendering a screen stays a read. It is given its host's state and journal, what media jobs run, and whether the session is open; the desktop's `Session` answers these requests through it;
- **the services a session may have** (`base/services.ts`, [D102](../decisions/D102.md)): which requests each holds; a request of a service the session does not have answers `not-available` with code `E_NOT_HERE`, and `summary.services` lists those it has (the desktop: all, `OpenOptions.services`);
- **the copy of a project in the cloud** (`base/session-cloud.ts`), written against its host and its store ([Projects in the cloud](sync.md#a-folder-linked-to-a-project)).

## Writes and reads
- **One write queue.** Commands (`run`, the journaled names of the CLI and MCP: `add_block`, `update_screen`…), `undo`, `undoBatch`, `mark`, restores, migrations, builds, what other writers did and media results run one at a time. Reads (`summary`, `readFile`, `listFiles`, `readScreen`, `screenParts`, `findText`, `conversions`, `translationStatus`, `translationTable`, `screenTranslation`, `diagnostics`, `history`, `renderScreen`) answer from memory and never wait for writes.
- **A write** runs in this order. A human or system write closes the open AI batch first (its `after-ai` version). The session takes an `auto` version when the newest is older than 5 minutes, then takes the project lock asynchronously (waiting for a CLI never blocks the event loop). It applies the journal's new entries and the files the watcher reported. The edit of `@elabora/node` runs with the session's snapshot (`files`, `validate: false`, `autoVersion: false`), and what it wrote (`written`) updates the snapshot without reading the folder. The session then reads its own journal entry back, releases the lock, pushes the canvas, validates, and emits `changed` then `diagnostics`.
- When an edit finds that a file it touches changed on disk unseen, it asks the session for its snapshot again, with the stale paths. The session journals the difference as `external` first, and the edit is computed again on the refreshed snapshot.
- **Publishing** (`build`: `mediaQuality`, `release`, `profiles`, `name`, all optional) makes the package as `elabora build` does (`<project>/dist`), in the write queue. The open AI batch closes, and what other writers left is journaled as theirs. The build then runs outside the project lock (encoding renditions can take minutes, and the CLI waits for the lock 40 s at most), with the session's validation options by default; renditions it encodes are reported as `mediaJob` events. The state keys it adds to `elabora.lock.json` are journaled under the lock as one `system` change (command `build`), so the watcher never reports them as an agent's `external` edit. A successful build takes a `publish` version, named after the day in the course language (« Publié le 7 octobre 2026 », "Published on 7 October 2026") unless `name` is given. The result: `ok`, `zip`, `size`, `report`, `summary`, `errors` (what stopped it, waived findings left out), `warnings` (what did not: a package too large for some LMSs while none is chosen…), `change`, `version`. Media jobs still running stop the build (`E_ASSET_MISSING`): the app waits for their `mediaJob` events. The queue waits for the build (1 to 1.5 s on an 87-screen course, longer the first time a quality's renditions are encoded).
- **A language's package** (`buildTranslation`: `language`, `allowMissing`, `mediaQuality`, `release`, `profiles`) generates the translated course as `elabora translate build` writes it, from the files on disk, into `<data>/translations/<lang>` (the project's data folder: never copied, never watched). It then builds the package as `build` does into `<project>/dist` (`<course>-<lang>-<version>-scorm12.zip`), in the write queue. Nothing of the source is written or journaled: the copy is generated again every time. The build is `refused` when texts are to translate, to review or stale, or when the translation has not placed the marker of a word anchor (D28), unless `allowMissing` (a draft: texts stay in the source language, anchors go to their line's start). Translations that break the text always refuse it. The result: `ok`, `zip`, `size`, `report`, `units`, `untranslated`, `unplaced`, `plan` (the translated plan in the package: `approved`, or `draft` until a person approves it: command `approve_translation`), `summary`, `errors`, `warnings` (as `build`'s: the package's findings for its LMS among them).

## Incremental validation
Every check of `@elabora/core/validate` is declared, in the order of the report, with its scope (`FILE_CHECKS` run on any project, `COURSE_CHECKS` once course.json loads):
- a **screen** check depends on one screen and on what screens share and rarely changes (course.json, plan, components, objects, theme, variables). It runs on the screens course.json lists, or with `screens: 'all'` on every screen file, listed or not (schema, declared id, backdrop variant). `readsOtherScreens` marks the few that also read blocks of other screens (events: `visited` conditions; figures and decoration objects: the first block of a duplicate id);
- a **project** check compares screens with each other or with the plan (ids, coverage, usage, exposition streak, suspend data budget), or reads what no screen holds (object code, component definitions, theme, generators, media). `readsScreens` marks those an edited screen can change;
- `createValidationContext(project, options)` builds what checks share once (registry, plan index, listed screens, blocks by id); `validateScreen(context, screenId)` returns the findings of one screen, `validateProjectChecks(context)` those of the project checks, and together they make up the findings of `validateProject`;
- loading, validating and compiling never throw on a project that parses but breaks its schema (a test runs seeded mutations through every reader): the validator reports it.

The session (`project-state.ts`) keeps the findings per screen and per project check and re-runs what a change can affect, by the rules a room's validation follows too (`@elabora/core` `validate/incremental.ts`, D86, which holds the shared pieces):
- **a screen file**: that screen's checks; the screens that mention an id whose element (block, layer, event, the screen itself) changed in it, as a JSON string in their file; the project checks marked `readsScreens` (the others keep their findings: object code and generators are not parsed again). When only screen files changed, the loaded project is the previous one with those screens replaced: the components, so the registry and the analyses of templates, stay the same objects;
- **an asset**, or a change of the media status (a job under way, an unreadable file): the screens that name it and every project check;
- **any other file**: everything. A test checks, edit after edit on two sample courses, that the findings equal those of a full load and validation.

## The browser engine
A session that answers the protocol from a browser's Worker, on a copy of a project of the cloud ([D103](../decisions/D103.md)): `src/browser/`, without Node, checked as the base is. `openCopy({ id, store, api, connect, services })` opens it on what its store holds (`BrowserStore`: the copy's link, what the room confirmed, its journal; `memoryCopy` keeps it in memory). Its reads, batches, renders and copy of the project are the base's; its changes are the copy's journal (`browser/copy-changes.ts`, [D104](../decisions/D104.md)): a command runs on the view (`executeCommand` of the table's command), is kept as an entry of the journal before anything shows it, then recorded in the copy's `SyncClient`; an undo is planned on that journal (`@elabora/core/ops/undo-plan`) and computed on the view. It has the services its host gives, none by default (`summary.services: []`). The conformance suite runs against it under Node (`test/unit/engine-conformance-browser.test.ts`) and in a Worker of Chromium (`test/e2e/engine-conformance-browser.test.ts`).

In a browser, `browser/worker.ts` is the Worker of one module: the page sends it `{ kind: 'open', api, team, project, seed?, services?, offline? }`, it answers `opened`, `held` (another tab holds the module: Web Locks, `elabora-copy:<team>.<project>`; nothing is written), `missing` (nothing kept, offline, and no seed) or `failed`, then speaks the protocol. Its store (`browser/idb-store.ts`, `openIdbCopy`) keeps in IndexedDB, one database a copy, the link, what the room confirmed and the journal, read whole before the session opens; an entry of the journal is written before anything shows it; the team's media are kept by hash in the origin's private file system (OPFS), written under a temporary name then moved, the writes of one hash one after the other. Where the origin has none (a private window of Safari, where `getDirectory()` throws), they are kept in IndexedDB instead, a Blob a hash in a database of their own, checked against their hash before they are kept; a module opens there as anywhere, and only the local models (aligners, voices) are refused (`E_LOCAL_AI_STORAGE`). Keeping the storage for good is asked by the window (`navigator.storage.persist`, which no browser's Worker has: D137). Both need a secure context. It reaches its room by `browser/room.ts` (elabora-cloud C101–C103): the room's WebSocket and every call of the API carry the web session's cookie, which no script reads, and the Worker holds no token. A copy the browser does not hold (a first opening, or what the browser erased) is taken from the room's project (`roomSeed`: its files at the room's head, the person, a new copy's id; `opened` says `taken`); its media come when something needs them (`medium(hash)`: kept in OPFS, else read from the team's media by hash and checked), never as a change brings them. A medium it has not taken is known all the same by what the room said of it ([D125](../decisions/D125.md)): its size, and its facts once a copy gave them, kept in the link by hash; the state holds it with them and with the verdict the copy computes (`fileMedia({ ...facts, size }, path)`), so that narration, the timeline and validation read it as a probed one. Without facts, it has its size and waits to be probed. It has the `canvas` service when the page names it ([D105](../decisions/D105.md)): `openCanvas`, `canvasView` and `closeCanvas` keep the desktop's state (`base/canvas.ts`, `SessionCanvas`, which takes a sink: the desktop's local host, the browser's events), and a render or a change of view goes out as an event, `canvasRender { id, render }` (`screenRenderOf`: its files by path, kind and hash) or `canvasView { id, view }`, which the window gives the canvas's page; `openCanvas` answers empty `url`, `base` and `token`, the page's words, which the window holds. The editor's miniatures (D130) ask the same service for renders given back rather than pushed ([D133](../decisions/D133.md)): `thumbRender`, `momentRender`, `blockPreviewRender` and `measureRender` (`base/thumbs.ts`, both sessions), each a `SceneRender` frozen at its view, at the course's reference size, with a version; the files it names are the relay's to serve to the canvas host from then on.Free objects are compiled by what the app's Worker gives as it loads, before the open message: it imports `browser/worker.ts` and calls `provideObjects(() => Promise<ObjectCompiler>)` (esbuild-wasm and the libraries objects import, D117); the function is called at the first object a page asks for, once (again only if it failed), so a module without a free object loads nothing. Without it, an object's code is `unavailable`. The media of a copy the room does not give (an example the app ships, opened offline) come the same way: the app's Worker calls `provideMedia((hash) => Promise<Blob | null>)` as it loads, and a medium is taken from what the copy kept in OPFS, else from that source, else from the team's media, checked against its hash, then kept (`idb-store.ts`, `medium`); one whose bytes do not match is refused, never kept. It has the `media` service when the page gives a media Worker (`mediaWorker` in the open message, and `aacEncoder` for a browser without its own AAC encoder, D106, D107, [D135](../decisions/D135.md)) and names `media` ([D108](../decisions/D108.md)): the media Worker (`browser/media/worker.ts`) probes and makes masters without network or secret, the engine's side (`browser/media/service.ts`, `BrowserMedia`) keeps them by hash with their facts and journals them. A request that takes a file carries its token, and the window posts the `File` beside it: `{ ...request, attachments: { [token]: File } }`; a token without its file is a bad request, never a path read (the desktop keeps its paths). It has the `align` service when the page also gives a models Worker and its runtime (`modelsWorker`, `ort`, `ortWasm`) and the models' origin (`models`), and names `align` ([D113](../decisions/D113.md), [D114](../decisions/D114.md)): `aligners` and `alignNarration` as at the desktop, the lines the core's plan gives (`@elabora/core/align/plan`), each line's audio read as samples by the media Worker and timed in the models Worker (`browser/models/worker.ts`: onnxruntime-web loaded by address, one job at a time), then written by `set_narration_words`, one change a line; a line's audio made in the session is timed at once when its language's aligner is kept. The models are downloaded from the origin the page names, checked by size and SHA-256 as they come, and kept in OPFS (`browser/models/store.ts`, usable without a session: « Éléments téléchargés » is the window's, `browser/downloads.ts`, [D137](../decisions/D137.md)); a phone has no aligner (`E_LOCAL_AI_PLATFORM`), a computer that says it has too little memory for a model is refused it (`E_LOCAL_AI_MEMORY`). It has the `voices` service when the page also gives the address where the app serves the local voices' catalogue (`voices`) and names `voices` ([D127](../decisions/D127.md)): the desktop's eleven requests, the generation the core's (`@elabora/core/voice/generate`); Pocket TTS's model kept in OPFS and held while a screen's lines are said, each line said in the models Worker, its take kept in OPFS (`elabora-takes/<copy>/…`, `browser/voices/takes.ts`) and written by `set_narration_audio` as the file beside the command, timed at once when the aligner of its language is kept; ElevenLabs is the core's provider through the page that holds the author's key (`browser/keys/`, `keys.elabora.studio`, [D136](../decisions/D136.md)), which the session reaches by a port the window transfers (`voiceKeyPort`; `setVoiceKey` only forgets the key there), and `voiceStandIn` puts tones in Pocket TTS's place for routine checks. It serves the relay of the web app ([D105](../decisions/D105.md)): `relayPort { host }` takes a relay host's port transferred with its message, and `browser/relay.ts` answers it from the copy, each host only what its pages ask for (the canvas the module's files; the frames host an object's page, its code compiled by the host's esbuild-wasm, its files and the module's assets).

## Where changes come from
The session above its changes is the same for every host; where they come from and go is not ([D101](../decisions/D101.md)). `base/changes.ts` says what a session asks of it (`SessionChanges`): a write apart from every other writer, after what they did is taken in and followed by what it wrote; what others did taken in between writes (`refresh`); new contents journaled as one change of their author (a media job's result, a version restored, the room's change); the journal's last number; what a program other than Elabora's tools left out or replaced (D75). It gives back the journal entries it took in, in order (`ChangesHost.taken`: the history and batches, the copy in the cloud, the `changed` events), and asks for validation after each change. The desktop's realization is the folder (`session-folder.ts`, `FolderChanges`): the project's lock, its journal, other processes' changes, files written by other programs, the watchers, as below. A browser's will be a copy of the room's project: what the room confirmed, then the changes waiting, the room's journal (`journalOf`), and no lock, other writer or watcher. How a command and an undo run is left open until that second realization is written: on the desktop they are `@elabora/node`'s edits, which append to the folder's journal themselves.

## Other writers
- **The journal first.** New entries (from the CLI and the MCP server, in other processes) are applied to the snapshot and never journaled again: each touched file is read back when its hash is the one the journal recorded after the change; a file written again since gets the journal's version (the operations applied), and the difference is journaled as an external change.
- **External edits.** The folder is watched (recursively) and listed every 15 s for what a watcher missed. `openProject` resolves once the folder's watcher reports (`onReady`; 3 s at most), and its first listing comes after: a file written once the project is open is reported at once. On macOS the watchers of a thread share one FSEvents stream. The stream is rebuilt whenever one of them starts or stops, and what is written meanwhile is never reported to any watcher of the thread (measured: writes from about 16 ms before to 10 ms after). So `FsStore` watches each folder from a worker thread of its own: a preview started or stopped, or another project opened or closed, in the same process takes nothing from an open project (`packages/engine/bench/watch-rebuild.ts`, an agent writing a file every millisecond over 10 previews started and stopped: 467 writes of 5786 lost with a shared stream, none with a thread per folder). The journal's watcher stays in the engine's thread; it is a shortcut: a change another Elabora tool journals also writes files, which the folder's watcher reports, and the journal is read before them. Reported paths wait for a quiet moment (60 ms, at most 600 ms during a burst: an agent writing 50 files makes one change); then, under the project lock, the files whose content differs from the snapshot are diffed (`diffFiles`) and journaled as one `external` change. A binary file modified less than 400 ms ago is still being written: the burst waits for it, up to 2 s, so that a video copied with the screen that shows it is one change.
- **The session's own writes** come back from the watcher; they are recognised by content, not by time: a reported file that holds what the snapshot holds is settled without the lock.
- **A JSON file that does not parse** (an agent mid-write) keeps its last valid content in the snapshot and the loaded project, with `E_JSON_PARSE` in its screen's findings (or the project's); nothing is journaled until it parses, and it is then diffed against its last valid content. A new file waits outside the snapshot until it parses (its creation is one change). A file broken since the session opened has no valid content to keep: its new text is taken without a journal entry.
- Conflict copies of sync services are set apart (`W_SYNC_CONFLICT_COPY`); tool folders and temporary files are ignored. A project folder moved or deleted while open is reported (`error` event) and nothing is written there any more.

## Batches and versions
- An AI batch is open while AI changes (`agent`, `external`) come in. It closes after 5 minutes without one, at a human or system change, at a mark, or when the session closes: the session takes an `after-ai` version and emits `batchClosed`. `mark(request)` (« Demander à l'IA ») closes the batch, writes the mark that labels the next one, and takes a `before-ai` version (the newest version when nothing changed since).
- Elabora's chat: `mark(request, author, chat)` opens a turn (the mark's id is the turn's batch; a mark another process appends with its chat opens one too). A turn's batch stays open through human changes, idle time and another AI's work; `endTurn({ turn })` closes it (`batchClosed` with reason `turn`, an `after-ai` version) and returns `{ batch, changes }` (`batch` null when the agent wrote nothing). The next mark of the conversation or the session closing also close it. A session opened during a turn (no `turn-end` in the conversation's transcript since its mark, less than a day ago) takes it up.
- Versions: `auto` on open and before a write when the newest is older than 5 minutes, and 5 minutes after activity resumes; `close` when the session closes; `migration` before a format migration; `publish` after a successful build (named, so kept until the user deletes it); a restore (`restoreBackup`) is journaled as one `system` change, after the `restore` version, so it can be undone. The project's data is pruned once per session (60 s after opening, or at close), under the project lock.

## Media
The session runs the project's media queue from opening. Files that unfinished jobs will write or replace are left to the job's result. When a job is done, its files are journaled (an import as its requester's change; a conversion as a `system` change holding the master, the removal of the original and the references rewritten by `replaceMediaReferences`, the original stored first so that undo brings it back). Media files of `assets/` carry their probe and verdict in the snapshot (new or changed files are probed, through the probe cache); the media status follows the jobs (the session's own, and other processes' at each listing), so `I_MEDIA_PROCESSING` replaces `E_ASSET_MISSING` while a job writes a file. Media that are not conformant masters are converted (option `media.autoOptimize`, on by default). At close, running conversions are cancelled (queued again at the next open, since the files are still not masters) unless `close({ media: 'wait' })`.

## Format
A course in an older format is read migrated in memory (`I_FORMAT_OUTDATED`; `summary().format` says what the migration changes). Option `migrate`: `ask` (default: the `migrate` request writes the migration, and an edit through the session migrates first, as the CLI does), `auto` (migrated on open, after the open version), `never` (writes are refused). A migration is one `system` change after a `migration` version (`migrateIfOutdated`, given the session's snapshot). A newer format is refused (`E_FORMAT_NEWER`).

## Rendering and the canvas
`renderScreen` renders through one render context per language. The context is kept while what screens share is unchanged (course.json, plan.json, elabora.lock.json, `components/`, object manifests, `theme/`, translations, the files its stylesheets name). Renders are memoised per screen and view, and forgotten when the screen file, a file they list (assets by hash, an object's folder) or a shared file changes. What the player's bars show that depends on every screen (the outline, the items that show, « IA et crédits », the languages) is kept apart per language, made again after a change to any screen or asset, and pushed with the screen shown when it changed.

- `openCanvas` starts the canvas host of the project (its page goes in a frame of the app).
- `canvasView` shows a screen or a language (a new render), or changes the state, step or layer shown (a view message: the page keeps its nodes).
- After every change that affects the screen shown, the session pushes it again, with the change's sequence number as render id.
- `closeCanvas` closes the canvas host.

The app's « Lecteur » tab adds `&chrome=live` to the page URL. The player's bars then work around the screen and speak `elabora-player-preview/1` with the app ([Rendering](rendering.md), *The player's preview*). A change of `player`, the resources, the glossary or the credits reaches them as any change of `course.json` does.

## Protocol

- events `{ kind: 'event', event }`: `changed` (source `engine`, `journal`, `watcher` or `media`; the change with its author, batch, files and operations), `diagnostics` (the screens whose findings changed, removed screens, the project's findings when they changed, the summary), `mediaJob`, `backupTaken`, `batchClosed`, `error` (a background task), `closed`.

```ts
// engine process
const session = await openProject(dir);
session.subscribe((message) => port.postMessage(message));
port.on('message', async ({ data }) => port.postMessage(await session.handle(data)));
// renderer
const client = new ProtocolClient((message) => port.postMessage(message));
port.onmessage = ({ data }) => client.receive(data);
const summary = await client.request('summary', {});
```

A request of a service the session does not have (D102) answers `not-available`, code `E_NOT_HERE`; `summary.services` names the services it has.

The protocol is checked by its conformance suite (`test/conformance/engine.ts`): each request at least once on the sample modules, judged on its answer and the events that follow, never on how a session does it, a last case failing when a request of `protocol.ts` has none. It takes a session as a target (a transport, how a picked file reaches it, where an export goes, the services it has: a case of another is skipped): the desktop's runs in `test/unit/engine-conformance.test.ts`, with the tests' stand-ins for its voices and transcriber; every other session that speaks the protocol runs the same cases.
