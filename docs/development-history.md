# Development history

## Unreleased — task-scoped agent guidance and skill discovery (2026-10-17)
- Course rules and the authoring/design skills are short task routers, with detailed recipes loaded on demand. Narration, translation and Storyline/Rise importing have focused skills. Unedited course rules update through D34's existing revision mechanism; author notes and edited rules are preserved.
- **`elabora tools skills [<name> [<reference>]] [--json]`** lists bundled skills or reads one skill/reference without a course. MCP exposes the same references at `elabora://skills/<name>/references/<reference>`; the agent guide describes both interfaces.
- Validation tests account for Windows crash exits, file permissions and folder enumeration.

## Unreleased — Windows browser worker captures (2026-10-17)
- Headless Electron workers on Windows use offscreen windows so repeated screenshots, contrast and fit measurements keep receiving frames. The app applies the same setting to worker popups.

## Unreleased — automatic word alignment progress and failures (2026-10-17)
- Voice generation emits a distinct `voiceProgress` phase `align` while a line's words are timed, including when an earlier take is selected. A failed automatic alignment keeps the audio and reports `alignmentError` on the line's result so editors can explain that its words remain estimated.

## Unreleased — compatible local model releases and Intel platform policy (2026-10-17)
- Optional local models select exact compatible releases, stage upgrades beside active versions and retain directory leases until inference finishes (D55). Workers switch directories between calls, and provenance records the release actually used. Update-only intent never reinstalls an absent element.
- Intel Macs retain editing, recordings, existing narration and media conversion; the core refuses installation and inference for local voice generation, word alignment and transcription on darwin/x64 (D54). Downloaded models remain removable. The app supplies update network policy and the shared status panel.

## Unreleased — the plan's versions: the plan written at any time, versions made by hand, one validated (2026-10-16)
Clean break before publication, with no migration: a plan written before it (with `status` and `approval`) breaks the plan's schema.
- **`plan.json` is the working copy** (D52), written at any time by the author and their agent: `write_plan` (CLI `elabora plan write`, MCP **`elabora_write_plan`**, in place of `draft_plan`, `elabora plan draft` and `elabora_draft_plan`), `set_plan_text` (`elabora plan text`: a validated text reworded, every block that shows it follows), `set_plan_voiceover` (always written), `revert_plan_change` (`elabora plan revert`, « Revenir à la V2 »). `status` and `approval` leave `plan.json`. An agent's write that changes a text kept « à l'identique » is refused (**`E_PLAN_VERBATIM_LOCKED`**). Commands know who runs them (`CommandContext.author`).
- **Versions** in `plan-versions/V<n>.json` (schema `plan-version`: `version`, `date`, `note`, `contentHash`, `plan`, `notes`, `sends`, `validation`): **`create_plan_version`** (`elabora plan version [--note]`) and **`approve_plan`** (`elabora plan approve [--version Vn] --by … [--reference] [--date]`, the latest version by default, never the working copy) are a person's: refused to an agent (**`E_PLAN_PERSON_ONLY`**), and no MCP tool does them. **`record_plan_send`** adds a send; **`set_plan_note`** (`elabora plan note`) writes a note for the client on a change in no version yet (`plan-versions/notes.json`, schema `plan-notes`), frozen with the next version.
- **What changed**, computed: `@elabora/core/project/plan-diff` `planDiff(base, current, course?)` (elements matched by ids, added, removed, moved from their position, an item's part changed, each field, texts word by word; the part an item belongs to, not the field it is written in: a plan without parts that writes each item's part down, as the app does at the first drag, changed nobody's part, which `planCourse(project)` lets the diff know by the course's sections that gave them) and `revertPlanChange`; `@elabora/core/project/plan-versions` (`planState`, `planVersionsView` with the changes since the validated version and those in no version, `planDiffBetween`, `notesFor`, `describePlanVersions`, `planContentHash`). CLI **`elabora plan diff [--from] [--to] [--json]`** and `elabora plan status [--json]`; MCP **`elabora_plan_diff`** (read-only); `elabora_get_plan` gives `versions` in place of `validatedOnce`.
- **Rules**: `E_PLAN_NOT_APPROVED` means a release build without a validated version; **`W_PLAN_MODIFIED_SINCE_VALIDATION`** replaces `E_PLAN_MODIFIED_AFTER_APPROVAL` (a warning: the build report's `plan.validated` and `plan.changesSince`, and the proof dossier, list the changes delivered); **`W_PLAN_VERBATIM_CHANGED`**; **`E_PLAN_VERSION_INVALID`** (a version edited by hand, not counted). Gone: `E_RETOUCH_VERBATIM`, `E_RETOUCH_WITHOUT_TEXTREF`, `I_TEXT_RETOUCHED`, `W_CHANGE_REQUEST_INVALID`.
- **Gone with them**: change requests (`changes/CR-*.json`, the `change-request` schema, `propose_plan_change`, `apply_change_request`, `reject_change_request`, `elabora change apply|reject`, MCP `elabora_propose_plan_change`) and retouches (the blocks' `retouch`, `retouch_text`, `restore_validated_text`, `approve_retouches`, `elabora plan retouch|restore|approve-retouches`, MCP `elabora_retouch_text` and `elabora_restore_validated_text`). `elabora rename` rewrites the plan's waivers that name the id.
- **The plan's document** (format `elabora/plan-document/2`) shows a version, the latest by default, or the working copy (`PlanDocumentOptions.version`, `planDocumentTarget`): its head says the version shown and the history up to it; the changes since the latest validated version read in place (`EntryMark`, `titleChange`, words deleted and inserted, elements added and removed), as Word tracked changes signed « Depuis la V2 validée », and the notes for the client as Word comments and margin notes. `exportPlanDocument`, `elabora plan export --version Vn|current`, `elabora_export_plan_document { version }` and the engine's `exportPlanDocument` record the send on the version shown (`ExportedPlanDocument.version`, `sent`) and never make one.
- **Engine**: requests **`planVersions`** and **`planDiff`**; `planDocument`, `planDocumentPage` (with the `version` shown) and `exportPlanDocument` take `version`; `summary.plan` gives `latest`, `validated`, `sinceValidated`, `unversioned`; commands `write_plan`, `set_plan_text`, `revert_plan_change`, `set_plan_note`, `create_plan_version`, `approve_plan`, `record_plan_send` (gone: `draft_plan`, `propose_plan_change`, `apply_change_request`, `reject_change_request`, `retouch_text`, `restore_validated_text`, `approve_retouches`).
- **A translated course** holds its approved translation as its own validated `V1`, and none of the source's versions.
- **Agents**: rule 1 and the workflow of the course `AGENTS.md` (revision 4), the authoring, pedagogy and free-objects skills and the MCP server's instructions: the agent writes the plan and says what it changed, never makes nor validates a version, never changes a verbatim text.
- The examples hold their validated version; `diagnostic-reseau` has V1 sent, V2 validated, two changes since and a note for the client.

## Unreleased — faster free-object gates (2026-10-07)
`elabora object test` (MCP `elabora_test_object`) had become the slowest check agents run: about 230 s for the 3D chart table of `medieval-charts` and 22 s for `diagnostic-reseau` on a Mac.
- **Where the time went** (Linux, 4 cores, no GPU: chart table 326 to 328 s, `diagnostic-reseau` 8.3 s). Nearly all of it was Chrome drawing the objects' frames in software (SwiftShader, which the gates keep: snapshots need the same pixels on every machine, and the boot budget speaks for machines without a GPU): 40 to 75 ms a frame for the chart table, about 5,600 frames a run, of which its snapshots look at 10. A `step` returned once its frames were queued, so their drawing was paid by whatever came next: a later step (up to 24 s), closing the page (72 s in all, for frames nobody would see) or a snapshot, which hit Playwright's 30 s timeout: the chart table failed its gates there, every run (« Three voyages complete the table »; with the stall guard's 60 s that `main` gave snapshots since, it passes in 309 s). Pages (0.1 s per test), axe (0.2 s), PNG comparisons (0.1 s) were negligible; mounting takes 0.3 to 8 s a test (its first frame uploads textures of 1,536 to 4,096 px), and stays: it is the boot time the gate measures.
- **Dry frames.** Frames no snapshot shows run dry: the object's code runs every frame (its state, events, uploads, shaders and their errors), its draws, clears and blits are skipped (`@elabora/player` `dry-frames.ts`, frame method `object/test-dry`, test mode only). What a skipped operation would have drawn is tracked as stale until drawn again; a dry run decides only when it passes and saw nothing that depended on it (a canvas still stale at a snapshot, a draw on a stale framebuffer or sampling a stale texture, `readPixels`, copies and blits of a stale drawing, a WebGL canvas drawn into a 2D canvas, uploaded or turned into an image, a query or `getError` after a skipped draw, transform feedback). Otherwise, and whenever it fails or a snapshot differs, the run is done again with every frame drawn, and that run decides; when only the drawing of a render target was reused, it is first tried again with render targets drawn and only the canvas dry, as are the object's next tests (`orbital-rendezvous` bakes its Earth into textures over the first frames: 134 s fully dry and drawn again, 48 s so). Runs that record baselines draw every frame. The 300 frames of the smoke gate, tests without snapshots and the steps after a test's last snapshot cost nothing to draw; a step before a snapshot draws its last frame only. `testObject(…, { allFrames: true })` draws everything.
- **A step waits for its frames** (a WebGL 2 fence: `gl.finish` is a flush in Chrome), so that every call waits for its own drawing and the 60 s stall limit applies to it; a snapshot no longer times out behind queued frames.
- **Snapshots through the DevTools protocol**: a PNG Chrome encodes for speed when it is only compared (lossless; the same pixels as Playwright's element screenshot, without the text caret as there; about 50 ms instead of 0.4 to 1 s), with the default compression when it is kept as a baseline: baselines recorded now are byte for byte those recorded before. Existing baselines stay valid: the chart table's ten and `diagnostic-reseau`'s two compare equal.
- **After**, on the same machine, against the gate runner of `main` (which since gives snapshots the stall guard's 60 s): chart table 309 s → 36 to 45 s, `orbital-rendezvous` phasing lab 288 s → 37 s, `diagnostic-reseau` 8.5 s → 4.2 to 4.9 s, every gate as before and every baseline equal (those of `main` included). Drawing every frame (`allFrames`), the chart table takes 322 and 331 s: the time goes away with the frames not drawn. What is left is mostly mounting, which the boot gate measures.
- **How each run was drawn** is in the result (`gates.frames`: `dry`, `dry on the canvas`, or `every frame (why)`: `records baselines`, `to confirm a failure`, `readPixels of a drawing a dry frame skipped`…), so that a slow test explains itself; it is not part of `object.gates.json`.
- **Boot times are measured as before** (the mount and its first frame, drawn). On this machine they come in steps of about 2.2 s whatever the code (chart table, medians of 9 from 0.7 to 4.5 s over runs of the same object, with or without dry frames; the slow-boot warning comes and goes): the time is in the object's first frame, which uploads its canvas textures through SwiftShader. Not changed here.
- Evaluated and left out: running behaviour tests in a GPU browser (the frames it would move are the ones now skipped; frames before snapshots must stay in software; without a GPU, as here and on CI, both browsers are SwiftShader), several pages at once (SwiftShader already uses every core: two runs together took 93 s against 112 s one after the other, and concurrent mounts would skew the boot samples), fewer page loads (0.1 s each), dropping the queued frames when a page closes (`Page.crash` hangs Playwright's close).
- Docs and skills: docs/free-object-contract.md (protocol, §6 *Frames drawn*), docs/architecture.md (*Rendering*), `elabora-free-objects` (draw every frame in tests, pick by raycasting rather than `readPixels`).

## Unreleased — Linux and Windows, found by CI (2026-10-07)
- **Project lock on Windows**: a lock file another process is deleting refuses to open or be created (EPERM) for a few milliseconds; the lock read that as an error and the writer failed. It now counts as a lock being released and tries again (writers in five processes, 100 increments, none lost).
- **Media on Windows**: a conversion's change lacked the removal of the original. Windows reports the folder of a file that changes, too. ## Unreleased — edits as operations, journal and undo (2026-10-06)
- **Every edit is a journaled change**: the commands of the CLI and the MCP server (`add_block`, `move_block`, `create_screen`…) are pure functions in `@elabora/core` `commands/`; `@elabora/node` `edit/` runs them under a project lock, as operations addressed by id (`@elabora/core` `ops/`), with their inverse, their author (`ELABORA_AUTHOR`, Claude Code, agent, human) and their batch, in `journal/<yyyy-mm>.jsonl` of the project's data folder. Edits return `change` (`id`, `seq`, `batch`); `undo` is the change's sequence number in the journal. The edit history of the prototype (`.elabora/history/`) is no longer read.
- **Undo keeps later edits**: undoing a change applies the inverse operations whose targets still hold what the change wrote and reports the others (`skipped`), instead of refusing when a file changed since. `undoBatch` undoes a batch of AI work (by default the last), `historyBatches` lists batches with the request that opened them, `appendMark` records that request; an undo can be undone. A hand-formatted JSON file comes back exactly as it was.
- **Automatic versions**: an edit takes a backup version just before writing when the newest one is older than 5 minutes, then prunes the journal (30 days) and the backups (`pruneProjectData`).
- **New errors** for refused edits: `E_LOCKED` (another writer holds the project), `E_CONFLICT` (a file changed on disk while the edit was computed; computed again twice first), `E_BLOB_MISSING` (a binary content is not kept), and `E_OP_TARGET_MISSING`, `E_OP_DUPLICATE`, `E_OP_NOT_KEYED`, `E_OP_NOT_JSON`, `E_OP_INVALID` for operations that cannot apply. Edit errors carry them in `code` and `diagnostics`.
