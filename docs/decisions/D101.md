# D101. Where a session's changes come from and go, behind one interface (18 Nov 2026)

A session's changes come from different places depending on its host. On a desktop, the folder is the truth: the project's lock, its journal, other processes' changes (the command line, the MCP server), files written by programs other than Elabora's tools (D75), watchers and rescans. A browser engine has a copy of the room's project instead (D73): what the room confirmed, then the changes waiting, the room's journal. It has no lock, no other writer and nothing to watch. The session above it is the same for both: one write queue, the project in memory, the reads ([D100](D100.md)), the AI batches, the events.

Decided:
- **One interface, in the base** (`@elabora/engine/base/changes`, `SessionChanges`):
  - a write apart from every other writer, after what they did is taken in, and followed by what it wrote taken in;
  - what other writers did, taken in between writes (`refresh`, `final` at close);
  - new contents journaled as one change of their author (a media job's result, a version restored, the room's change);
  - the journal's last number;
  - what a program other than Elabora's tools left out or replaced.
  It gives back the journal entries it took in, in order (`ChangesHost.taken`). The session records them (history, batches), gives them to the copy in the cloud and tells them (`changed`, with where each came from), and validates after each change (`afterChange`).
- **The desktop's realization is the folder** (`session-folder.ts`, `FolderChanges`), its code moved from `session.ts` as it was: the lock, the journal's tail, other processes' entries applied, the external changes computed and journaled, the watchers' reports reconciled, the folder listed again. The desktop's session also uses what only the folder has: the lock and a sync without a write (a first upload, a build), the journal read again after pruning, the entries it appended itself.
- **Left open: how a command and an undo run.** On the desktop they are `@elabora/node`'s edits, given the session's snapshot, which append to the folder's journal themselves. In a browser a command runs on the view and is recorded in the `SyncClient`, and an undo is computed from the room's journal and the changes waiting. The interface takes them in when the second realization is written. The commands' table is being reworked meanwhile.

Weighed:
- **The command's run in the interface now.** Rejected for now: its shape on the desktop is the edits' `EditOptions`, which the commands' rework changes, and its shape in a browser is not written yet.
- **One class for both, with branches.** Rejected: a browser has none of the folder's machinery, and each branch would be tested on one host only.

*Revisit if:* the browser engine needs from its changes something the interface does not say, or the desktop's session reaches into the folder for more than the lock and the journal.
