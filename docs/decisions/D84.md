# D84. The commands by name, with the schema of their arguments, in the core (12 Nov 2026)

A project's room in the cloud ([D73](D73.md)) runs commands sent by name with their arguments, and the tools an agent writes with through the cloud are those commands. Both kept their own list of the core's functions by name, and the tools' schemas lived in the command line's MCP server: a renamed argument or a new command could reach one and not the others.

Decided:
- **One table in the core** (`@elabora/core/commands/table`): the commands that need nothing but the project's files, by the names the journal, the command line, the MCP tools and the engine give them (47 today). Each entry holds what a tool says of the command, the JSON Schema of its arguments, whether it removes content (`destructive`), whether it is a person's only (`personOnly`: making and validating a version of the plan), and the core function that runs it. `namedCommand(name)` finds one by its own name only (nothing inherited); `COMMAND_NAMES` lists them.
- **One source for the MCP tools.** A tool whose arguments are the command's takes its description, schema and hint from the table; the catalogue the MCP server lists did not change by a byte. Tools that read as well as change (`elabora_player`), or take other arguments (`elabora_ignore_finding`, `elabora_translate_text`, `elabora_translation_approve`), keep their own, the player's built from the table's.
- **The compiler checks each schema against its command**: the arguments a schema allows must be what the command takes. A test runs every hand-written schema's arguments, nulls included, through the command on an example course.
- **Data and functions only**: no validator, nothing done at load. The schemas use the helpers of `@elabora/core/commands/arguments`, which the MCP server shares.

The schema is what a tool may send, not a gate: every command checks its own arguments and refuses with `CommandError`, and arguments from elsewhere (the journal, the app) are run by the command, not checked by the schema.

Weighed:
- **The table in the engine** (which already maps names to edits). Rejected: the engine's run on a folder, under its lock; a room has no folder.
- **The commands that need a computer** (templates, fonts, a library's components, media, sounds). Left out: a room cannot run them; they stay the engine's.

*Revisit if:* a room needs a command that reads more than the files (a template the room keeps); the tools of the cloud need words the local ones do not.
