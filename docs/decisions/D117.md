# D117. A free object's code is bundled by a part that needs no Node, given esbuild and its libraries (18 Nov 2026)

`@elabora/node` bundled an object's `object.js` (its relative imports, `three` and its add-ons as globals, D3 and the chart kit as libraries) with the native esbuild, from the object's folder, and kept the plugins that make it a classic script in the same file as the folder reading. A host without Node and without a disk (a page of the web, which has esbuild-wasm and the project's files in memory) could not use them, and wrote them again.

Decided:
- **`@elabora/core` `objects/bundle.ts` holds what does not touch a disk**: the build options, the plugins (three and its add-ons as globals, D3 and the chart kit as libraries), the resolution of an object's relative imports in a table of files (`compileObjectFromFiles`), the add-ons an object may import and the page of its frame (`objectFrameHtml`). It imports no esbuild and no `node:` module (3 KB bundled, with `util/html`), so a browser's worker takes it as it is; the host gives it the build function (`ObjectBundler`: esbuild's `build`, native or wasm) and where D3 and the kit come from (`ObjectLibraries`: the source of an ES module, or a path for a host with a disk).
- **`@elabora/node` `bundles.ts` keeps the disk**: `compileObjectCode(dir)` is the native esbuild on the object's folder with D3 and the kit found on this disk, and `objectLibrarySources()` gives D3 and the chart kit as the source of two ES modules, bundled whole and unminified, for a host that has none (the web app builds them once).
- **The same code from both.** A test (`test/unit/object-bundle.test.ts`) bundles the objects of the examples both ways: the same bytes minified; not minified, the same code but for the comments that name each file by its path. esbuild-wasm is a development dependency of the repository at the version of the native esbuild (`0.28.2`), for that test.
- **One thing the native bundler reads that a table has not**: the nearest `package.json` of the object's folder. With `"type": "module"` (this repository's own, above its examples) esbuild bundles an import of CommonJS as Node's ES modules do (a `"use strict"` and a flag on its interop helper); a module in the author's library has none above it. The test copies the examples out of the repository for that reason, and the table's way is the library's.

Weighed:
- **Prebuilt, minified D3 and kit for the browser.** Rejected: an object would carry all of D3 whatever it uses; unminified and whole, the object's own bundle shakes and minifies them as it does from the disk, to the same bytes.
- **Passing esbuild's own plugin types.** Rejected: the core would depend on esbuild for types; the plugin is declared by its two calls and esbuild's and esbuild-wasm's types both take it.

*Revisit if:* esbuild-wasm and the native esbuild part ways on a version, or an object may import something the three globals and the two libraries do not give.
