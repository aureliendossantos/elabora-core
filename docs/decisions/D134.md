# D134. A block added without a slot goes in a slot that takes it (26 Nov 2026)

`add_block` used to leave a block without `slot` in the default slot, and an editor that puts a new block after the last one copied that block's slot. On a layout whose last block sits in a slot that takes only a free object or an image, and only one, « Text » with nothing selected put a text there: two `E_COMPONENT_SLOT` errors (the type, and the slot over its `maxBlocks`). An editor does not know the slots' rules; the core's registry does.

Decided:
- **Without `block.slot`, on a screen with a layout or in a component instance with slots,** `add_block` puts the block in the first of these slots that takes it: the slot of the block it follows (`after`), the default slot, then the declared slots in order. A slot takes a block it accepts (a fork where its parent is accepted, the validator's rule) while it holds fewer blocks than its `maxBlocks`.
- **A slot named is the caller's**, kept as given. In a layer (no slots), nothing changes.
- **When no slot takes it,** the block goes in the default slot as before, and validation says why: a command writes, the validator judges.
- The block preview of an editor (`blockPreviewRender`, D133) goes through the same `addBlock`: preview and result agree.

*Revisit if:* an author wants a new block to go somewhere the rule does not pick (then an editor names the slot), or a layout's slots overlap so that « the first that takes it » surprises.
