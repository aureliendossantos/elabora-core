# D73. Projects in the cloud: a server per project orders the changes, each copy shows what it confirmed with its own changes on top (12 Nov 2026)

A project can live in the cloud, with several people and agents working on it at once: people in the desktop app, agents on a person's folder, later agents in the cloud through a connector. The truth of such a project is on the server; each folder is a copy that also works offline. No CRDT: an arbitrary tree of course files, undo of an agent's batch after a person's edit and the validation of the whole project need one place that decides the order.

Decided:
- **One server per project orders changes** written in the language of [operations](../architecture/operations.md). It keeps the head (the files), a log of numbered changes and who is there. It places a submitted change once (by its id), refuses a base it no longer keeps (`E_SYNC_BASE`), rebases the change on its head ([D74](D74.md)), validates the result with a validation it is given (`E_SYNC_INVALID` when the project gets an error it did not have), recomputes the inverse on head, numbers the change and sends it to everyone. A change whose operations were all left out is placed too, empty, so that its copy learns why.
- **The protocol `elabora-sync/1`** (`@elabora/core` `sync/protocol.ts`): `hello`, `submit`, `catchup` and `presence` from a copy; `welcome`, `ack`, `change`, `refused`, `catchup`, `snapshot` and `presence` from the server. A placed change carries the operations kept and their inverse, `skipped` (left out) and `overwrote` (a person's values replaced by another person who had not seen them, so that their author is told). Server numbers are their own field (`seq` of `Committed`), not the local journal's.
- **A copy is a pure function of what the server confirmed and its waiting changes.** What it shows and writes is computed again after every change, never patched in place, so that every copy ends with the server's bytes.
- **One change in flight per copy.** The next waiting change is rebased on confirmed just before it is sent: its base is exact, the server meets only the changes of others, and what the copy's own rebase overwrote travels with it (`Submission.overwrote`).
- **Offline**, waiting changes pile up; on reconnecting the copy catches up from its number (or from the project as it is, when the server no longer keeps that far back), recognises its own changes by id, then sends the rest in order.
- **Authors come from the connection.** A change's author gains `id` (a person's stable id) and `by` (for an agent, the person who launched it). The rule of rebase depends on the author's kind: the server sets the author from the session that sent it, never from the submission.
- **Pure and shared.** `acceptChange`, `rebase` and `SyncClient` are in `@elabora/core` `sync/`, without I/O: the room of the hosting and every copy run the same code. The core is public, so the language of changes and the copy's side are too; the room itself stays with the hosting.
- **The convergence bench** (`test/unit/sync-convergence.test.ts`) is the gate of this model: two copies, a server in memory, people, agents and file edits drawn from a seed, a copy offline and back. Every rule here and in D74 and D75 was found or confirmed by it; seeds that once failed stay as fixed cases.

Weighed:
- **The server rebases a whole queue sent at once** (each waiting change with the base it was made on). Rejected: a change made on top of a waiting one that lost operations carries values of before that were never placed, which the server would read as conflicts with others.
- **A CRDT (Yjs, Automerge, Loro).** Rejected: none undoes an agent's batch after a person's edit, and a project must validate as a whole after every change.

*Revisit if:* one change in flight makes a fast typist wait on a slow network (send a short run of a person's changes as one); a project grows past what one server keeps in memory.
