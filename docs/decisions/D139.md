# D139. A miniature in a browser is an image a painter draws, kept by its version; the live frames are its fallback (27 Nov 2026)

[D130](D130.md) showed a browser's miniatures as live frames of the canvas page, at most eight. Measured on the list of a module of 62 screens: eight live frames keep +226 to 269 MB at rest in Chromium and Chrome and +78 to 88 MB in Firefox, and WebKit keeps about 1 to 4 MB for each document a frame loads, never given back (+1.4 to 1.5 GB after the list is walked). A frame given its renders by message, without loading again, costs nothing more (408 renders: +13 MB). Images made by one frame kept for them keep +14 to 47 MB at rest in Chromium and Chrome, nothing in Firefox, +461 to 478 MB in WebKit.

Decided:
- **A painter draws the miniatures as images.** It is one frame of the canvas page in `mode=thumb&painter=1`, kept in the view, above the page, and clipped to a pixel (a browser draws no frame out of the view, and Chrome gives a covered frame of another origin about one animation frame a second). It loads its page once and is given each render by message; it never loads again or navigates. It answers the question `picture` with the screen's pixels (`canvas-picture.ts`): drawn by `drawElementImage` where the browser has it, which the page finds out when it runs (on by default in Chrome stable, measured in Chrome 158), and by snapdom elsewhere (Firefox, Safari). Firefox draws the copy snapdom makes before it has decoded the images inside (their text shows in their place): when the page has loaded an image or a font since its last picture, a first copy is made and set aside. A page whose route to the module's files did not open draws without them: its picture is a failure, never an image kept for its version.
- **snapdom 3.8.3 (MIT) is vendored**, pinned and read before a new version replaces it (`pnpm run vendor`, `packages/node/vendor/snapdom-3.8.3.js`, its licence beside it, NOTICE). 331 KB, about 119 KB compressed. The canvas host serves it as `canvas/elabora/vendor/snapdom.js`, and only a painter's page loads it, only where `drawElementImage` is missing. Course packages do not ship it. Its code holds the addresses of Google's icon fonts; the canvas page's policy (`connect-src 'self'`, `font-src 'self' data:`) lets it reach nothing outside the canvas host.
- **Pixels only cross the origins.** The answer is a `Blob` that the host accepts only as `image/webp` or `image/png` (a WebP where the browser writes one, a PNG in WebKit) and shows only in an `<img>`. Never an SVG or markup: an SVG opened as a document runs in the app's origin. The image is an object URL, so the window asks for images (`createThumbs({ images: true })`) where its page allows `img-src blob:`, and gets the live frames otherwise; a page that asks without allowing it shows no broken image: it is a failure, said, and the live frames take over.
- **Its life.** Made as the miniatures are (the module opening), so that its page loads and a new profile's slow first frames pass before the list shows. In WebKit it lives as long as the miniatures (each document it would load again would stay in memory). In Chromium and Firefox it goes after `PAINTER_IDLE_MS` (30 s) without a picture and is made again when asked: the retouches of a working session do not pay a new painter each, and a list at rest gives its memory back. There it is also made again after `PAINTER_PICTURES` (8) pictures: a page that draws grows and gives nothing back while it lives (about 90 MB for eight pictures in Firefox), so that one painter kept down a list of 62 screens reached +1 GB in Firefox and +0.8 GB in Chromium, against +0.28 and +0.7 GB made again. The picture that makes a new painter pays 50 to 100 ms more (a retouch shown after 183 to 270 ms instead of 128 to 175): one in eight.
- **Images kept by version** ([D133](D133.md)'s, which leaves out the outline's titles): in memory, the least used first out past 48 MB, those an element shows never. A retouch changes the version of its own screen only, so only its image is drawn again; a row seen again shows its image at once. A scene in the view that has no image for its version is drawn, one at a time, in the order of `thumbs-order.ts` (a preview first, the editor's screen, then reading order). A scene out of the view, or in a hidden tab, waits. No image outlives the session: a cache kept in the browser would be one more copy of a module left there once the author signs out, and the first view already takes about a second.
- **What D130 kept holds.** A block's scene is the part around the block (`mini`: the block alone) and gives `overflow`, from the same `block-preview` logic. A miniature at rest does no work: the painter's page is `mode=thumb`, held still once each screen is drawn. A free object stays its box with its name. The measurer stays a live frame.
- **The window's contract does not change** (`host.captures.show`). The limit of eight live frames now holds only for the fallback.
- **The live frames of D130 are the default and the fallback** (`createLiveThumbs`): where the window does not ask for images, where the browser has no `OffscreenCanvas` or `createImageBitmap`, and, for every scene, once the painter has failed twice in a row, said in the log (`ThumbsOptions.log`, by default the console's warnings), never in silence.

*Revisit if:* the first view grows slow enough to want images that outlive the session (then kept by account and erased at sign-out); WebKit gives back the memory it keeps under pressure, or Safari itself measures otherwise than Playwright's WebKit; snapdom needs a new version; or `drawElementImage` changes its form again.
