# D118. The relay's protocol: the questions a host answers about a module's files, and the messages that carry them (19 Nov 2026)

On the web the canvas is a page of an origin of its own, and so are the free objects' frames. The files of the open module (images, videos, fonts, the compiled code of an object) are nowhere on those origins: a service worker, the relay, asks for each of them through a message port, and the app's engine answers. The desktop's local server answers the same questions from the project's folder. Both must give one answer to one question.

Decided (`@elabora/player` `relay-protocol.ts`, types and the few functions both ends need; no Node, no dependency):
- **Three questions, one vocabulary** (`RelayRequest`): a `file` of the open module by its path, whole or a `range` (from `start`, to `end`, or the `last` bytes); the page of an object's frame (`object-frame`), which the core writes (`objectFrameHtml`, D117), served as it is; the compiled `object-code`. A `RelayAnswer` is a file (`type`, `size`, `hash`, `body`: a Blob, which a browser's storage hands over by reference, or a string; `part` when the body is only some bytes of the file, as a medium taken in pieces from the server) or a refusal (`not-found`, `refused`, `unavailable`, `failed`: 404, 403, 503, 500). A host implements `RelaySource.get(request, signal)`: the engine of the browser over its storage, the desktop's server over the folder (a later piece); `relayPathOf`, `relayRequestOf`, `parseRange`, `resolveRange` and `relayResponse` are the one place that turns a URL into a question, a `Range` header into bytes and an answer into an HTTP status and headers, for the relay and for the desktop's server alike (D120).
- **The relay answers a request with a `Range` with `206`, and one without never with `206` or `416`** (the relay's part; Safari asks a medium by ranges and requires `206`). A range the engine did not take into account is applied by the relay to what it was given.
- **A route per view of a module**: a random key (`isRoute`: 128 bits or more, base64url) that the app makes for one module open in one tab. The app's page gives each relay page (the canvas page, and the frames host's hidden page) one port per route (`relay/open`, the port with it); a request is answered by the port of its own route, never another's. The relay page takes `relay/*` messages from its parent only, at the app's exact origin, and checks them (`parseAppToRelay`): another protocol or a route that is not one is answered `relay/refused`, and anything from elsewhere is not answered.
- **A port carries `relay/request`, `relay/cancel` and `relay/done` one way, `relay/answer` and `relay/bye` the other** (`relay/done`: the page closed the route, and the engine forgets the port; `relay/bye`: the module closed). What comes through a port is data: `parseRelayRequest` refuses a path that leaves the module (`..`, a leading `/`, a backslash, a NUL) before any source sees it, and `serveRelayPort(port, source)` is the engine's end: it checks, asks the source, answers, cancels a request the browser gave up, and ends with `relay/bye`, or with no word at the page's `relay/done`.
- **A version replaces another without reloading the app.** The ports live in the pages, not in the service worker, which keeps nothing: a new script installs and takes the open pages over, and each page says `relay/ready { version }` again. The version is opaque and changes with the script; the protocol (`elabora-relay/1`) changes only when these messages do. The app, whose build knows the protocol it speaks, sends `relay/update` to a page that runs an older script, and the page answers `relay/updated` with what runs.

Weighed:
- **One request per kind of file, decided by the host.** Rejected: an object's frame page and code are not files of the module; saying so lets the engine build them (the core's `objectFrameHtml`, the bundler) and the relay serve them without guessing from a path.
- **The relay slicing a range from a whole Blob only.** Rejected: a medium the engine has not taken yet is fetched by range from the server; `part` says what was given.
- **A route per tab chosen by the service worker** (from its clients). Rejected: a frame's page is a navigation, which has no client of the app above it to name; the route in the frame's address is the app's to give (D119).

*Revisit if:* the engine needs to answer something that is not a file of the open module (a listing, a thumbnail), or a medium's answer must stream rather than hand over a Blob.
