# D119. The relay: one service worker for the canvas host and the frames host, a route per view of a module, and what its pages and a free object's code can and cannot do (19 Nov 2026)

D118 fixed the questions. This decides who asks them, for whom, and what the relay may be made to do. The relay is code that pages written by authors and agents can call and unregister: it must give nothing but the open module of its own tab.

Decided (`@elabora/player` `worker/relay.ts`, `relay-page.ts`, `relay-link.ts`; built by `@elabora/node` `relayFiles()` into `relay.js`, `relay-page.js`, `relay.html` and the canvas page):
- **One script, `/relay.js`, for both hosts.** The host's Worker writes `self.ELABORA_HOST = Object.freeze({ policy, frameAncestors, appOrigin })` before it: its whole `Content-Security-Policy`, its `frame-ancestors` directive and the app's origin. Without that line the relay answers nothing. The relay reads `appOrigin`; when a host leaves it out it falls back on the one origin the host's `frame-ancestors` names (the canvas host's), and when there are several (the frames host's) it has none: its pages take no message and no port, and the app hears nothing. The relay pages take `relay/*` messages from their parent at that exact origin only.
- **Every answer the relay makes carries the host's policy**, `frame-ancestors` included, `Cross-Origin-Embedder-Policy: require-corp`, `Cross-Origin-Resource-Policy: cross-origin`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. The browser then checks every frame above a page the relay serves, whatever page of the app's site is at the top (the security review's M1): a review page that frames a space that frames the canvas's answer shows nothing (a test, with its negative control: the same answer without `frame-ancestors` shows).
- **A route is a secret of a tab, not the only guard.** The app makes two routes (D118) per view of a module in a tab, **one for each host**: the canvas's goes in the canvas page's address alone (`?route=`), and is held by the canvas page; the frames', which the canvas page reads as `?framesRoute=`, goes in the address of each object's frame (`?route=`, `frames.ts`), and is held by the frames host's relay page. The canvas's route is never given to the frames host nor written where code of an author reads it: a frame that knows its own route knows nothing that the canvas host's relay answers to. A request is answered by the one relay page that holds its route: the route comes from the frame's address (a navigation), or from the address of the page that asks (the canvas page, a frame's document). `frame-ancestors` stays on every answer, a page at the top is never served (404), and the route enters no message, no error, nothing the relay says to a page that did not name it: an unknown route, an unheld one and a refused one all answer the same 404 or 503.
- **The service worker never broadcasts.** It keeps, in memory, which page holds which route (`relay/hold`, said by the pages at the paths `/relay.html` and `/canvas/index.html` only, and again when the worker wakes: its `relay/awake`, which carries nothing, goes to those pages). A request goes to the page that holds its route, never to every page: a `matchAll` followed by a message to all would tell a route to the code of an object of another tab, which is a client of the same origin. A route a live page holds is not taken by another.
- **A free object's code can take over the frames host's page, and what that gives it is bounded.** The object's frame is of the frames host's origin (it needs `allow-same-origin` for the relay to serve it), and so is the hidden relay page the app puts in a frame there. The frame reaches that page by `top[i]` (indexed access is allowed between origins), and with the host's policy (`script-src 'self'`) can load a script from the relay (an object's own code, served as `object.js`) into it: from then on the code is the relay page. It can take the ports of the routes the page holds, read what the app says to the page, answer the relay's requests and speak to the app as the relay page. The bounds:
  - **A port gives nothing a frame has not.** The frames host's port answers an object's frame page, its code and the files of `objects/` (`hostMayAsk`, `serveRelayPort(port, source, 'frames')`: the engine's end refuses the rest before its source sees it); the module's other files go by the canvas host's port, which no code of an author reaches (another origin; the canvas runs the player's scripts only), and that port asks files only (never a frame's page or code: they are the frames host's). One source answers both, a port each; the host is told when the port is served.
  - **An object's frame never asks for a file under `assets/` (the module's), and the rule is `objects/` only.** What a frame asks of the relay by itself is its page, its code (`object.js`) and, at most, files of its own folder (`objects/<id>/…`: the manifest's declared assets are paths in it, loaded by its markup, which its policy limits to `'self'`). The course's files that an object reads (an `asset` setting, the fonts) it does not fetch: it asks the host with `ctx.host.asset`, and the canvas page, whose port answers all the module's files, fetches the bytes and gives them (`object-host.ts`); `connect-src 'none'` stops the frame from fetching anything itself. If a frame came to need a file outside its folder, the rule would be widened by naming that file's kind here, not by a prefix.
  - **The app's window must hold, in a tab, the frames host's page for the routes of one module only**: a page that held the routes of two modules would let an object of the first read the second. This is the window's to keep (the web app's window), one relay page of the frames host per module open in a tab.
  - **The app takes what a relay page says as data** (`parseRelayToApp`): a version, `ready`, `opened`, `closed`, `refused`, `updated`, `error`, nothing else, nothing longer than 500 characters, a route only in the shape of one. A taken-over relay page can make the app believe that the relay runs another version (it may ask for an update, which looks for the real one), that a route opened or closed, or that the relay failed; none of it opens a file, changes a module or shows anything to the person that the page did not already show. Nothing important depends on it: the files a module serves are the engine's, by the port it holds.
- **A frame served in an opaque origin was tried and does not work.** The relay answering a frame's page with `Content-Security-Policy: sandbox allow-scripts` would take the relay page, the host's storage and the worker's registration out of the object's reach. In Chromium 153, WebKit 26.6 and Firefox 155 a sandboxed frame's own requests (its script, a `fetch`) do not go through the service worker, and it has no storage: it cannot load `object.js`. The bound stays as above.
- **What the frames host's storage allows between two modules of one browser** (for the security review): IndexedDB, `localStorage`, `BroadcastChannel` and the cache of `frames.elabora.page` are shared by every object of every module a person opens there (and so are the canvas host's by the canvas's scripts, which are the player's). The code of an object of one module can read and write what another module's objects keep, and message them. The relay keeps none of it, and the module's files do not travel through it; it is the same as the desktop's local preview, where the frames share one origin.
- **A version replaces another without reloading the app, and what makes a new script reach a relay that is already installed** (it is what happens at every deploy):
  - The host's Worker serves `/relay.js` with `Cache-Control: no-cache` and `Service-Worker-Allowed: /` (C105). A browser fetches a worker's main script past its HTTP cache whenever a page in its scope loads (and at least once a day), and installs it if one byte differs: a deploy reaches an installed relay at the next load of the canvas page or of the frames host's relay page, with no action of the app. The script's version is the release and a hash of its code (`relayFiles()`), so one byte is a new version.
  - The new script calls `skipWaiting()` at install and `clients.claim()` at activation: it takes the open pages over without a reload. **The ports live in the pages, not in the worker, which keeps nothing**: they survive. Each page says `relay/ready { version }` again at `controllerchange` and says to the new worker which routes it holds; the new worker's `relay/awake` makes every relay page say it too, and a request that comes before they have waits up to 2 s for its route's holder.
  - The app can ask for it at any time (`relay/update`: the page calls `registration.update()`) and learns which version runs (`relay/updated`, and `relay/ready` with the new one). **A newer script can be held back by the events of the pages, and the page asks it again.** Found by a loop of the test (one pass in eight to twenty-four failed, the same symptom once in Firefox), with a trace of the browser's service worker states (CDP `ServiceWorker.workerVersionUpdated`) and of every event the worker received: the browser stops the running script to activate the new one; a `fetch` event of a page (a frame loading `object-frame.js`: a pass-through of a file of the host's own is still an event) or a message reached the running script in that instant and started it again, and the new one stayed `waiting` (`installed`, never `activating`) until the running one had been idle for the browser's own time. The remedy is in the page, not in the worker's code: it says nothing to the running script while a newer one takes over (a message is one more event), and while the newer one waits it asks it, every 1.5 s, to skip waiting again (`relay/skip`, which only that waiting script answers), which makes the browser try again; 20 s at most, then it says what runs (`relay/updated`). A newer script found by the browser itself (a page of the host loaded after a deploy: `updatefound`) is taken over the same way. The test hammers both hosts with events while the version is replaced: without the nudge one pass in six failed, with it none in twenty-four.
  - A relay older than the app's protocol or newer than it is answered `relay/refused { reason: 'protocol' }` by the page and heard by the app (`elabora-relay/1` changes only when the messages do); the app then asks for an update or says to reload.
  - Tested: a version replaced in an app that stays open while events keep coming (a marker of the page is kept, the routes work, both relay pages report the new version), twenty-four passes in a row in Chromium, and in WebKit and Firefox.
- **A request of a module's file never goes to the network.** A request under `/canvas/` that is not the host's own file and whose route is not yet held (a page that asks for an image in its first task; a worker just woken, whose pages have not said again what they hold) waits for its route, as long as an answer of the engine does (`RELAY_ANSWER_MS`), then is answered 503. And a page that the relay does not control yet (the first visit, the worker not installed) is given nothing to ask: the page host (D121) sends the first render only when both relay pages hold their route's port, which is when the worker controls the pages. Found in the window: a portrait and a font were asked of the canvas host's network, which answered 404.
- **A 503 says why.** A request the worker answers 503 (or 500) tells the relay page that holds the route, as data (`relay/fault`: the path, where it failed, what was caught: `holder` no page holds the route, `ask` the page could not be asked, `answer` the answer was refused or could not be made a response), and the page tells its app (`relay/fault` in `RelayToApp`, read by `parseRelayToApp`, heard by `onRelay`). Never to a module's frame, and the route is not in it. Found with it, in WebKit: the 503s of an example's font and portrait on a second visit were a request that came before its route was open (the worker then waited 300 ms): the rule above, not a medium that does not survive its passage (`test/e2e/relay-engine.test.ts`: the engine's own Worker keeps the sample's media and serves them whole and by ranges through the port, the page and the service worker, a second visit from what it kept, in a WebKit profile on disk; without the engine's `move(folder, name)` it answers 500).
- **Range.** A request with `Range` is answered `206` with its range (`416` when it lies past the end), whatever the engine returned (the whole file, or only the part it had: `part`); one without never `206` or `416`; several ranges, or a malformed one, the whole file. Safari asks media by ranges and needs `206`; what is left to see there is in the report.

- **What the relay gives as a page, and what as a script (the security review, S1 and S4).** A module's file is given to what shows or reads it, decided by the request's destination (`relayMayServe`, one function for the relay and the desktop's server): an image, a font, a style, a sound, a video, a track, a plain fetch. A document, a frame, an embed, an object, a script, a worker and the rest are refused (403), a navigation to a file whatever it is for too. Only the frame page of an object is a navigation (to a frame), and only the code of an object (`object.js`) is a script. Every answer built from a module's file also carries `X-Content-Type-Options: nosniff` and the host's policy with `sandbox` after it (no script, an origin of its own: if a browser ever loads it as a page all the same, it is inert). The frame page of an object is the one answer without `sandbox`: it must run, and what bounds it is the frame's own `sandbox` attribute (the player's list of words, D119 below, `allow-same-origin` for the frames host's origin only), the frames host's policy (`script-src 'self'`, `connect-src 'none'`, `frame-ancestors` the canvas and the app) and the port, which gives its page only `objects/`. The desktop's server judges the same way from the header `Sec-Fetch-Dest` when a browser sends one. **If the canvas ever needs an author's page or script** (a PDF shown in a frame, a component's code), it is a decision of its own, with its destination and its bound, taken then: nothing is opened for it now.
- **The words of an object's sandbox are the player's list, not the manifest's** (`SANDBOX_PERMISSIONS`, `frames.ts`, `objectFrame`): `pointer-lock` and nothing else. A word that is not on the list, or that carries a space, is dropped whatever validation said, because a copy or a package that was not validated would otherwise give an object `top-navigation`, `popups-to-escape-sandbox` or `downloads`. For a valid module it changes nothing (the schema admits `pointer-lock` only); on the desktop and in a published package the same function builds the frame's `sandbox`, so the same words are dropped there.
- **Anything ever given to the frames host's relay page is given to the objects' code.** It is of the frames host's origin, and an object reaches it by `top[i]` (`hostMayAsk` bounds what its port asks, the page's own state is the object's to read). Give it no capability, no secret and no route but the frames'.

- **The frames the host puts in the window are sandboxed** (the security review, S8). The hidden page of the frames host's relay is of the origin where an object's code runs, which holds it (S5, accepted): with no `sandbox` attribute it did what the object's own frame is forbidden to do, with no gesture of the author (a notice in the author's words, a download, windows opened at an address of the object's choosing). It now carries `sandbox="allow-scripts allow-same-origin"` (`RELAY_FRAME_SANDBOX`): its script and its origin, which its service worker is, and nothing else; its ports, its messages to the app and the service worker's registration are untouched (Chromium, Firefox and WebKit). The canvas's frame, which only the player's code fills, takes `CANVAS_FRAME_SANDBOX` (`allow-scripts allow-same-origin allow-pointer-lock`: the pointer lock is for the frames of objects inside it, which can have no flag it has not), given to the window as `info.sandbox` to put on the `iframe` before its `src`: no popup, download, modal, form or navigation of the window. The Lecteur's preview (`chrome=live`), when it is shown there, will need `allow-popups allow-popups-to-escape-sandbox` for a link of the course and `allow-downloads` for a file; a published module's player is another matter and is not touched.
- **`relay/fault` is data that an object may have written.** The relay page of the frames host is the object's to drive (S5), so a `relay/fault` that reaches the app may be forged: whoever reads it later (the app shows it, logs it, counts it) takes its path, stage and message as text from an untrusted source, bounded in size, never as the service worker's word.

Weighed:
- **The route in the frame's address, or a worker that finds the app above the frame.** The second is not possible: the app is of another origin, `clients.matchAll()` does not show it. Rejected.
- **A route per object frame.** Rejected: nothing keeps an object of a tab from reading another of the same module, which it can already.
- **The worker keeping the routes in a store.** Rejected: the same origin's code reads it, and a route kept is a route readable.

*Revisit if:* an object needs a file outside `objects/`, the frames host moves to an origin per module (then the storage line goes), or a browser stops giving a service worker the page's address.
