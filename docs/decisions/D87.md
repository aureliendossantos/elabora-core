# D87. An undo carries what it left out, through a project's server (12 Nov 2026)

An undo leaves out the inverse operations whose target was changed since ([D79](D79.md)): they stay in force, and a later undo tries them again. The journal of a folder keeps that list with the undo. A submission did not carry it, so the server's log counted every undo as complete: an agent of the cloud, which undoes from that log, found nothing left to take back after a first undo that kept a person's edit.

Decided:
- **The list travels with the undo**: `Undoes` (`sync/protocol.ts`) gains `skipped`, the inverse operations it left out, each naming the change it is the inverse of, as the log holds that change. The copy that computed the undo sends it (the engine's session from its journal, with the ids the server knows); the server keeps it in the placed change.
- **Each rebase on the way adds what it left out.** The copy's rebase before sending and the server's as it places the change report the operations they did not place whole (`RebaseResult.left`), and add them to the list (`leftByRebase`), named after the undo itself: they are its own operations, matched against its targets' inverses when the state is read.
- **One reader for a server's log**: `journalOf(log)` gives journal entries for the core's undo rules (`undoState`, `changesToUndo`, `lastStep`), an undo with what it left out; `undoState` reads a left-out operation named after the undo against every change it targets.
- **A run sent as one change, undone whole.** A copy sends an agent's run as one change ([D83](D83.md)), and its undo names each change of the run: `journalOf` reads an undo that names every change of a run as the undo of the run's entry. An undo of only some changes of a run leaves the run in force in the server's log (its operations cannot be told apart there).
- **An undo goes alone.** The changes an agent makes after its undo, in the same batch, were sent with it in one submission ([D83](D83.md)), so the server took them for part of the undo; now an undo is never grouped.
- **Proved** by the case of the connector (an agent's batch, a person's edit kept by its undo, the person's edit taken back, the agent's undo again: the kept value goes, and a third undo finds nothing), the same with the person's edit reaching the server between the agent's reading and its undo, a copy's rebase leaving part of an undo out, a linked folder's undo, and the convergence bench with agents undoing their batch from the server's log: every operation left out resolves to an inverse of a target, and nothing in force before an undo vanishes after it without being applied (240 draws in the suite; 800 once).

Weighed:
- **The undo computed by the server** from its log, on its head (no rebase, so nothing to add). Not needed: a copy's undo is computed where its author saw the project, and the reader makes the server's log tell the same; an agent of the cloud already computes on the head.
- **Mapping what a rebase left out to the change it undoes** (an origin per operation). Rejected: the operations an undo sends are its targets' inverses, so matching them reads as well, with one limit: an insertion or a move placed after another anchor no longer matches, and counts as undone.

*Revisit if:* an undo reaches inverses of changes the server's log no longer keeps (10,000 changes back), or a person undoes in the app the work of an agent of the cloud (its changes come in as the room's).
