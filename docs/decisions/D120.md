# D120. The desktop's local canvas server answers the relay's questions from the project's folder (19 Nov 2026)

D118 gave the web app's relay and its engine one vocabulary for the open module's files. The desktop's local canvas server answered the same questions in its own way (a table of allowed paths, a function for files, a function for ranges, its own page for an object's frame and code).

Decided (`@elabora/node` `canvas/source.ts`, `canvas/host.ts`):
- **The server is a `RelaySource` over the folder** (`folderRelaySource`): the files that the pushed renders listed, and the narration and sounds the editor plays whatever the screen shown; an object's frame page (`objectFrameHtml`) and its code (`compileObjectCode`), both only for an object a render listed; nothing else of the folder. A file is a Blob that reads the disk as it is used (`fs.openAsBlob`), so a range reads the range; its entity tag is its size and time, and the page revalidates every time.
- **The HTTP of an answer is written once** (`relayResponse`, `@elabora/player` `relay-protocol.ts`): the relay's service worker and the local server both turn an answer into 200, 206 with a Range (416 past the end), 304 on the server, and never 206 or 416 without a Range. The Range header is read in one place (`parseRange`, `resolveRange`); `byteRange` is gone, and the servers that stream a file from the disk (`serveFile`: the preview, the LMS emulator) use the same two functions. The media types were already one table (`@elabora/core` `MIME_TYPES`).
- **A URL becomes a question in one place** (`relayPathOf`, `relayRequestOf`): the server refuses a path that leaves the module (`..` segments, a backslash, a NUL) as the relay does, where it used to normalise it.
- **The desktop does not change.** The same pages, the same files, the same headers of a file (type, length, entity tag, `Accept-Ranges`, `no-cache`), the same refusals; the editor's canvas e2e pass as they were. What it loses is the `Last-Modified` header of a file, which the entity tag replaces.
- **The two sources agree**: a test (`test/unit/relay-sources.test.ts`) asks the folder and the browser engine's source for the files, an object's frame page and its code (esbuild-wasm for the browser's) and finds the same types, sizes and bytes; the folder refuses a file no render listed (it holds more than the module), the engine's copy has only the module.

*Revisit if:* the desktop's server must answer a question the web's engine does not, or the relay needs a header the folder cannot give.
