# D131. The relay keeps its host's own files, named by their SHA-256, so that the canvas opens without the network (26 Nov 2026)

The web app's shell starts without the network (its service worker keeps its files), but the canvas page and the player's files come from the canvas host, and an object's frame needs the frames host's: the canvas stayed empty offline. D119 had the relay keep nothing.

Decided (`@elabora/player` `worker/relay.ts`, `relay-link.ts`; `@elabora/node` `relayFiles()`):
- **`relayFiles()` gives every file of the two hosts**: the relay's script, the relay page's script, the frames host's page, the canvas page, the player's script and stylesheet, the objects' frame script and three.js. The hosts serve the same set. The relay's script names the others by their path on the host and the SHA-256 of their bytes (`__RELAY_FILES__`), and its version changes with them.
- **The relay keeps them**, as it installs, in a cache named by its version (`elabora-relay-<version>`), and serves them from it with the headers the host gave them; it deletes the caches of other versions when it takes over. A file not kept yet is asked of the network and kept if its bytes are the ones named. The first visit is still online: the canvas opens without the network after it.
- **A kept file is served only once its bytes are the ones the script names.** Any script of the host's origin can write in its cache, and an object's code runs on the frames host (D119, S5): a file of the cache is checked once per waking of the worker, then held in memory; one that does not match is asked of the network again (unreachable: the request fails, the bytes in the cache are never served). Tested by writing another three.js in the frames host's cache from an object's frame, stopping the workers and loading it with the host unreachable.
- **The relay runs under a policy of its own.** It fetches its host's files itself, which `connect-src 'none'` (the frames host's pages) forbids. The host's Worker serves `/relay.js` under `default-src 'none'; connect-src 'self'` and says it in `self.ELABORA_HOST.workerPolicy`; the pages keep the host's policy. The relay keeps its files only when the policy it runs under lets it fetch its own origin (`mayConnectToSelf`): a host that has not changed serves its files as before (the canvas host's policy already allows it, the frames host's does not).
- **What it does not keep**: anything of a module or a person (the module's files still come from the engine through a route, and are never kept), the relay's own script (the browser keeps it).

Not decided: names that carry their hash (`canvas.<hash>.js`). A page loaded under one version that loads a file late (an object's frame asking for `object-frame.js` after a new relay took over) gets the new version's file, as it did from the network before; the objects' frame script and the canvas page speak a versioned protocol. Hashed names would need the engine, which writes an object's frame page, to know the frames host's names.

*Revisit if:* a late file of a new version breaks a page of the old one (then hashed names, the old version's cache kept until its pages are gone), or the first visit must work offline (then the app's shell would carry the hosts' files).
