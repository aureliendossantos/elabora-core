# D106. Media in a browser: a Worker of its own, the rules both hosts read in the core (19 Nov 2026)

The browser engine ([D103](D103.md)) imports and probes media without ffmpeg. An encoding of twenty seconds must not freeze the session, and what decides on a file (its facts, its verdict, its metadata) must be what the desktop decides.

Decided:
- **The media's code lives in `packages/engine/src/browser/media/`**, without Node, checked with the rest of the browser engine. It runs in **a Worker of its own, started by the engine's Worker at the first request**; the engine's open message gives its address (`mediaWorker`): the app bundles and serves both. Without it, the session has no `media` service.
- **The media Worker makes no request to the network and receives no secret.** It reads `Blob`s, writes to the origin's private file system (OPFS), and answers the engine's Worker, which sends to the team. The only things it loads are its own script and, when it is given, the address of the AAC encoder ([D107](D107.md)).
- **The browser's probe gives the desktop's facts** (`MediaInfo`, as `@elabora/node` reads them from ffprobe): images from their headers, videos and sounds from their containers by Mediabunny, nothing decoded. A test compares both on files made by the native ffmpeg, field by field, in Chromium, Firefox and WebKit (`test/e2e/media-probe-browser.test.ts`).
- **What both hosts read the same way is the core's** (`@elabora/core/media/`): a reader asks ranges of a file and returns its answer (`media/bytes.ts`), the desktop answering from a file handle, a browser from a `File`'s slices. The EXIF orientation, the GPS position (EXIF, XMP), the image without its metadata, an MP4's top-level boxes are read there; the desktop's bytes stay the same (`test/unit/media-metadata.test.ts`). The silence rule of a narration line and a PDF's title come down the same way when the browser needs them.

*Revisit if:* a browser's probe must decode to know a fact, or the media Worker must reach the network itself.
