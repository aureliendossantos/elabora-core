# D93. A role changed while connected: the room says it, the copy takes it (12 Nov 2026)

A person made a viewer while working learned it only when the room refused their next change (`E_SYNC_READ_ONLY`), and that change left the module; made an editor again, nothing said it. elabora-cloud's protocol promised that open connections « take the role at once (a `role` message) », and the core had no such message.

Decided:
- **`{ type: 'role', role: 'owner' | 'editor' | 'viewer' }`**, a server message sent to each open connection of the person whose role changed (`RoomRole`). Nothing at connection: the copy's role is unknown until the room says one, and the copy writes as before.
- **The copy takes the role.** A viewer's own changes (an agent's, a file edited in the folder: the app refuses its own edits for a viewer) wait in the copy instead of going to a room that would refuse them; `settled()` resolves once online, since nothing more can be sent. Made an editor or an owner again, what waited goes, rebased as after a time offline (D73). `session.cloud.role` says the role, and the engine emits `cloudRole` for the app.
- **A copy older than the message ignores it**: `SyncClient.receive` answers `ok` to a type it does not know (its `default`), and the session goes on; such a copy learns a demotion by the refusal, as before.

Weighed:
- **Dropping a viewer's changes at once** (the room would refuse them anyway). Rejected: a demotion by mistake, undone a minute later, would cost what an agent was writing.
- **The role in `welcome`** (known from the first message). Left for later: the window reads the team's role when the module opens, and a change while connected is what needed a message.

Amended the same day: **the copy says its status (`cloudStatus`, with `pending`) as soon as it takes a change of its own, and when the room says a role.** Alone in a project, the window heard that a change waited only at the room's next message (a presence), so a viewer's kept change was never said.

*Revisit if:* a role other than these three appears, or a viewer's waiting changes should be offered to someone else rather than kept. Done for keeping them beyond the connection: the role in `welcome` (D94) tells a copy opened as a viewer, demoted or promoted while offline, before it sends anything.
