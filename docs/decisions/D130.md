# D130. A miniature in a browser is a live frame of the canvas page, at most eight, asked for through one call of the host (21 Nov 2026, revised 26 Nov)

The desktop shows a miniature as a capture of a hidden page (`captures.thumbnail`, an image kept on disk). A page cannot capture a page, and no browser renders a page's DOM to an image without a screen capture (`getDisplayMedia`, a permission every time; `OffscreenCanvas` draws no DOM; `<foreignObject>` redraws the page wrongly). A miniature in a browser is therefore a **frame of the canvas page** (`/canvas/index.html?mode=thumb`), at the course's reference size and scaled to its element, given a frozen render by message. The types are in `thumbs-protocol.ts`; `createThumbs` (`canvas-thumbs.ts`) is the browser's side.

Decided:
- **One call for the window** (`host.captures.show(module, scene, element)`, `CapturesShow`), a scene being a screen, a screen at a moment, a screen with a block or a charter variant. The desktop's host puts its capture in an `<img>` of the element; a browser's host calls `createThumbs`. The window has no `if (web)`.
- **At most `THUMB_LIMIT` (8) live frames**, nearest to the view first, the screen of the canvas first; the others keep their skeleton. A frame is 25 to 60 ms of drawing and 150 to 300 ms to load; eight cost +277 MB in Chromium, +133 MB in Firefox and +272 MB in WebKit, sixteen +441, +238 and +561 MB (a quiet Mac, a course of 62 screens). Sixteen was the limit first; it was found too much memory for an editor's tab. A view of more than eight miniatures (the Planche shows 9 to 12) draws the eight nearest its middle, the others drawn as the author scrolls. **Fallback if eight is still too much:** a « sheet » page, one canvas page that holds every screen as a document of its own of the same site (8 MB each, 3 times faster, measured), which needs the canvas's singletons undone (`#t-main`, the document's listeners): not now.
- **A frame outside the view is not drawn** (Chromium and WebKit never answer, Firefox in 96 s) and **moving an `<iframe>` reloads it**: a frame lives with its element, and is made only for an element in the view (`THUMB_SETTLE_MS`, 120 ms, the nearest to the view first, the editor's screen before any), destroyed with `release()`. `createThumbs` watches the view itself (an `IntersectionObserver`): **a frame whose element left the view stays while a place is free**, so a row that comes back is drawn at once, and when an element in the view needs a place and none is free, the frame farthest from the view goes. A refresh asked for out of the view is drawn when the element comes back. The window calls `show` when an element is mounted and `release()` when it goes; a window that releases rows as they leave the view is right too, it only keeps nothing.
- **A block's preview is framed as the desktop's capture is** (« Ajouter un bloc »): once the screen is drawn, the canvas fades the block's neighbours and scrolls to it (`block-preview`), and the element shows the part of the page around the block, or the block alone for the list's small box (`mini`). `ThumbShown.overflow` says whether the slide runs past the window with the block in it, from the first drawing. A miniature of the Charte is the whole window.
- **A frame kept in place is given a new render by message, never recreated**, and at most once every `THUMB_REFRESH_MS` (400 ms), `THUMB_REFRESH_PARALLEL` (2) at a time, the screen of the canvas first: a retouch in the canvas does not redraw every frame at each keystroke. A thumbnail already drawn at the render's `version` is not drawn again.
- **A free object is not mounted in a thumbnail**: its block is drawn as its box with the object's name. **This is where a browser's miniature differs from the desktop's capture**, which shows the object running. A video shows its poster, a sound nothing, a narration does not run.
- **The security review's rules hold**: a miniature is the canvas page itself (no new kind of document, no author's file as a page or a script), without the frames' route and without objects; one route and one port of its own for each frame (at most eight more, files only); the canvas's sandbox words, `inert`, `pointer-events: none`.
- **The engine gives the render** (`ThumbRequests`: `thumbRender`, `momentRender`, `blockPreviewRender`, `measureRender`) and declares the files it names to the relay's source.

**Measured again on a Mac (26 Nov 2026)**, with the engine's renders and the relay on the hosts' real names, on a course of 62 real screens: on a quiet machine the list of screens (8 in view) is filled in 0.30 s in Chromium, 0.41 s in Firefox 157 and 0.73 s in WebKit; after a fast scroll the view is filled within a second; sixteen live frames cost +440 MB (Chromium), +240 MB (Firefox), +560 MB (WebKit). The desktop captures one screen at a time (about 0.24 s each) and then reads its cache. Chrome's experimental `drawElementImage` (HTML drawn in a canvas, an origin trial) would let one frame give images instead (62 screens in 6.6 s, 9 KB each): a second path once it ships.

*Revisit if:* eight frames are still too much memory (the sheet page), the miniatures come to be drawn as images by a server (then the live frames are the fallback for what has no image yet, at most four), or an author's object must show in a thumbnail without a server (a poster the object publishes).
