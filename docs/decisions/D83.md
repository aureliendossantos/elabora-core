# D83. A folder linked to a project in the cloud: the engine's session syncs it; an agent's run goes as one change (12 Nov 2026)

A project in the cloud ([D73](D73.md)) has copies on people's computers: a folder each, where the app, the command line, agents through Elabora's tools and programs writing files all work. The copy must send what any of them does and take in what others do, offline too, without a second writer beside the engine.

Decided:
- **The link.** A folder is linked to one project of a team (`elabora cloud project create`, `push` into an empty project, or `clone` into a new folder); the link lives in the project's data folder (`cloud-project.json`, never sent): the server, the team and project, this copy's id, its person ([D78](D78.md)), the room's number it has, what the room confirmed (by hash, in the folder's blob store), the changes waiting and the journal's last entry taken in. A first upload sends the media (four at a time, [D88](D88.md)), then the files in changes of at most 3 MiB, `course.json` last, so that no change adds an error the room would refuse.
- **The engine's session syncs** (`session-cloud.ts`; `elabora cloud project sync`, `--watch` to keep going). It takes every journal entry in order (its own, other processes', the external changes of [D75](D75.md)) into the core's `SyncClient`, and writes in the folder and its journal what the room changes, as the change of its author (command `sync`: never sent back, even after a restart). One invariant, kept in one place: the folder is the client's view; every step that moves it runs in the session's queue, under the project lock, after the journal's new entries. A change made here and refused by the room leaves the folder at once (the folder follows the view), and the refusal is told (`cloudOutcome`); its text stays in the journal.
- **Ids.** A submission's id is the copy's id and the journal entry's: sending it again after a crash or a lost acknowledgement is placed once.
- **Media.** A change that writes a binary file announces its media to the team and sends what the team lacks before it goes; a medium another copy wrote is read from the team before the folder is written.
- **An agent's run goes as one change.** With one change in flight, an agent's burst of a hundred small changes took about twelve seconds to reach the room on the test server (one round trip each); the waiting changes of one AI batch by one author now go together, rebased one after the other, as one submission naming them (`command: changes`), up to 100 changes, 600 operations or 2 MiB: the same hundred took 1.6 s. A person's changes still go one by one (each is its own batch, and its own step of ⌘Z).
- **On a test server only.** Rooms are not open on Elabora's hosting: the commands need the server's address (`ELABORA_CLOUD_URL` or `--api`) and refuse `api.elabora.studio`.
- **What stays as written.** A JSON file a program wrote in its own formatting keeps it in that folder; the other copies get Elabora's formatting: the folders hold the same values, not always the same bytes.

Weighed:
- **A sync process beside the engine** (reading the journal and the folder on its own). Rejected: two writers, and the engine already reconciles external edits, tails other processes' journal entries and holds the lock.
- **Each change in flight alone.** Kept for people's changes; for agents' runs, rejected by the measure above.

*Revisit if:* the app shows the copy's state and who is there (the screens wait for mockups); a text over 1 MiB must be edited by operations (today it travels as a medium); several sessions sync one folder.
