# D141. A component template renders without what the validator refuses (27 Nov 2026)

A component template is HTML a person or an agent writes in the project. What it may not hold (links, forms, frames, scripts, media, event handlers, addresses other than its own SVG's fragments, a style that is more than custom properties) was refused by the validator only (`E_COMPONENT_TEMPLATE`), and the renderer put the rest of the template into the page as written. The validator is no longer a frontier: the room keeps a person's change with its errors (the cloud's rule for agents is the copy's own word), and a plan waiver could waive the code. A link that leads the window elsewhere would then reach every frame that shows the module, and a published package.

Decided:
- **One list, said and enforced** (`components/template.ts`): `TEMPLATE_FORBIDDEN_TAGS`, `templateElementRefused`, `templateAttributeRefused`. The validator reports from them; `renderTemplate` leaves out a refused element with what is inside it, and a refused attribute. An image's `src` renders only when it is one binding to an asset prop.
- **In an SVG**, `script`, `style`, `foreignObject` and an animation that would set where a link points (`set` or `animate…` of `href`) are refused too, said and left out.
- **`E_COMPONENT_TEMPLATE` cannot be waived** by the plan: a build stops on it, as on the contract's other errors.
- **A style takes numbers and tokens only** (since 27 Nov 2026, `styleBindingAllowed`). Allowed are a number prop, a list's `@index`, `@number` and `@count`, and a token prop whose value is a token's name. A text bound in `style="--a: {{t}}"` would add declarations, for example an image of another site that a package or an LMS would load for every learner. The validator says it of a binding's kind, and the renderer leaves out a value of another kind with its custom property. Cleaning the text instead was weighed and rejected: it would keep a channel of free text into CSS (escapes, comments, `var()`), while the templates shipped bind only numbers, counters and tokens there.
- **MathML is never a template's** (`<math>` and what is inside it): maths come from a Markdown prop.
- Markdown props are not concerned. They render through their own rules, inside the elements that remain.

Every template shipped (23 projects, 188 screens, 27 component examples) renders byte-identical.

Weighed:
- **Sanitise the whole rendered HTML** (a DOMPurify in the player). Rejected: it would remove what blocks and Markdown put there on purpose (a video block, a link of a Markdown prop), and it would hold a second list.
- **Refuse the change at the room.** Not enough alone: a project made before, a package built from a copy, a waiver.

*Revisit if:* templates gain a construct that points elsewhere on purpose (a link component), which would then come with its own checked prop.
