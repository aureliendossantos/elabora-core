# D121. The host of the editor canvas for a page: what links a window that has no local server to the canvas page and the relay (19 Nov 2026)

On the desktop the engine opens the editor canvas with a local server (`@elabora/node` `canvas/host.ts`): it pushes the renders to the pages, asks them what they show, and the window frames the page. In a browser the canvas is a page of an origin of its own, framed by the app's page, whose files are served by the relay (D118, D119). Something must hold what links them, for the window not to know which of the two carries its canvas.

Decided (`@elabora/player` `canvas-page-host.ts`, `createPageCanvasHost`; no Node, importable by the app):
- **It has the desktop host's shape**: `push(render, { id })`, `view(view, { id })`, `ask(name, params)` over `postMessage`, plus `post(message)` for the author's gestures (scroll, focus, lift, motion, the player's preview), `onMessage(listener)` for what the page says, and `info { url, base, token }`, which is the desktop's `CanvasInfo`. The window frames `info.url` (it adds its own options, `scrollbars=none`, `placing=editor`), gives the frame to `attach(frame)`, and posts to `info.base` with `info.token` as it does on the desktop.
- **It holds the relay's side**: the token and two routes, one for each host (128 random bits each: the canvas's, in the canvas page's address as `route`, and the frames', in the same address as `framesRoute`, which the page puts in the address of each object's frame, D119), the frames host's relay page (a hidden frame it puts in the element the window gives, `mount`), and for each relay page a `MessageChannel`: one end goes to the engine by the window's `relayPort(host, port)` (the engine client's `relayPort { host }`, the port transferred; the engine serves it with the host named, D118), the other to the relay page by `relay/open` at the page's exact origin. It does this each time a relay page says `relay/ready` (a page loaded again, a new script of the relay), and says `relay/close` to both when it closes. `opened` is a promise of both ports held; `relays()` says each page's state and version; `update()` asks both to look for a newer script.
- **It sends the first render only when both relay pages hold their route's port** (`opened`): until then the page is not controlled by the relay's worker (the first visit) or its route is not open, and the files the render lists would be asked of a network that has none of them. The renders, the views and the questions wait for it; the author's gestures do not. A relay page that says it cannot serve (`relay/error`: a browser that gives it no service worker, as Playwright's Firefox does to a page after the first load, or a private window) is not waited for: the render is given all the same, drawn without the module's files, and the app reads the error (`relays()`, `onRelay`). The page says so itself, without the worker, after 5 s without a controller; it sends the sentence to whoever frames it (the host's `frame-ancestors` has said that is the app) and nothing else.
- **It keeps what a page loaded anew lacks**: the last render with the view as it is now (sent again on the page's `elabora/ready`, with its styles unless the page has them already), and the questions asked meanwhile.
- **One host, one module.** The frames host's relay page it puts in the window holds the routes of the one module it serves (D119): the window makes one host per module view and closes it with the module.
- **What the window gives it, exactly**: `canvasOrigin` and `framesOrigin` (exact origins: `https`, or `http` on this computer, two different ones), `mount` (an element of its page), and `relayPort(host, port): Promise<void>`. The window relays the engine's events to it (D123).

Weighed:
- **The window making the route and the channels.** Rejected: that is a second realisation of what the core must keep (the route's shape, the port per host, the order of `relay/open`); one host keeps it once.
- **The host creating the canvas frame.** Rejected: the window's canvas view remounts its frame as its views change (a frame, a scale, a fade-in); the host follows a frame that is given, and gives the page its render again.

*Revisit if:* the window needs two canvases of one module at once (then one route per canvas, and the frames host's relay page holds both: still one module).
