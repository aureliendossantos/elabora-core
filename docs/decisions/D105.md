# D105. The browser engine's relay: a port per route and host, given by `relayPort`; its canvas by events (19 Nov 2026, revised 19 Nov 2026)

The relay of the web app ([D118](D118.md)) asks the open module's files through a `MessagePort`, one for each view of a module in a tab and for each relay host (the canvas page, the free objects' frames). The engine of the browser ([D103](D103.md)) answers it from its copy. The engine's protocol must take that port.

Decided:
- **`relayPort { host: 'canvas' | 'frames' }`**, a request of the protocol whose message carries the port transferred with it (`postMessage(message, [port])`; `handle(message, ports)` receives it). It answers `{}`; the port is then served (`serveRelayPort`) until the session closes, which says `relay/bye`. Without a port, or with another host, it is a bad request.
- **One source per host, which serves that host's pages only what they ask by themselves** (`browser/relay.ts`, `relaySource`). The canvas gets the module's files: texts as they are, media by their hash (kept in the browser, else taken from the team's media, D104), with their media type (`@elabora/core/util/media-types`, shared with the desktop's local servers). The frames host gets an object's frame page (`objectFrameHtml`), its code and the files an object loads (its own folder, the module's assets), never a screen or the course; an object is refused on the canvas. A medium the browser does not hold and cannot fetch now is `unavailable`.
- **An object's code is compiled by the host's esbuild-wasm** (`CopyOptions.objects`: the bundler and the libraries objects import, D117), once per object while its files stay the same. Without it, the code is `unavailable`: the engine does not carry esbuild-wasm itself.
- **Not a service.** The supervisor's word was the `canvas` service, but that service's requests (`openCanvas`, `canvasView`, `closeCanvas`) belong to the window in a browser, and a service had is one whose every request is answered (D102). `relayPort` is the session's own: the browser answers it, and the desktop, which serves its canvas from its local server, answers `not-available` with `E_NOT_HERE`.
- Ranges are applied by the relay to the whole medium for now; taking a large medium by ranges from the team's media (C103, `part`) comes when the window plays one.

**Revised the same day: the browser engine has the `canvas` service, by events.** Its page is held by the window (`createPageCanvasHost` of `@elabora/player`), so the engine answers `openCanvas`, `canvasView` and `closeCanvas` with the desktop's state (`SessionCanvas`, now in the base: the screen shown, its state, step, layer and moment; the render made again after a change that affects it), and sends what the desktop pushes to its local host as two events the window gives the page: `canvasRender { id, render }` (the render as the page takes it, `screenRenderOf`: its files by path, kind and hash) and `canvasView { id, view }`. `SessionCanvas` takes a sink (`open`, `push`, `view`, `close`): the desktop's is its local host, the browser's the events. `openCanvas` answers `{ url: '', base: '', token: '', view }`: those words are the page's, which the window holds. The service is announced when the host names it, since it answers all its requests (D102). `relayPort` stays the session's own. The desktop does not change.

*Revisit if:* a medium must reach the canvas before it is whole, or the canvas's questions (measures, block previews) must be asked from the engine in a browser.
