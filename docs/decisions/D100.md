# D100. The session's base without Node, and a project's copy behind its store (18 Nov 2026)

Two engines will speak the engine's protocol: the desktop's, in its Node process, and a browser engine, in a Worker. What neither needs Node for must be one code both run, or they will drift apart. The first piece is the copy of a project in the cloud (D73, D83): its machine (reconnections and their waits, the room's close codes 4003 to 4008, a restored room's epoch, presence) was already written against its host and its connection, but it read and wrote the folder through ten functions of `@elabora/node` `cloud/projects`.

Decided:
- **The base lives in `@elabora/engine`, under `src/base/`** (`@elabora/engine/base/<file>`). Its files import `@elabora/format`, `@elabora/core`, the engine's `protocol.ts` (types only) and each other: never a `node:` module, `@elabora/node`, `process` or `Buffer`. `packages/engine/src/base/tsconfig.json` checks them without Node's types (`pnpm run typecheck`). Unlike `@elabora/core` they keep state and timers: a session's machinery, not pure logic.
- **A copy asks its host for a store** (`@elabora/core/sync/copy`, `CopyStore`): the files the room confirmed, keeping the copy (its link, what the room confirmed, of it what changed), unlinking it, the team's media sent, committed and fetched by hash, and whether its person still reaches the project. What the copy remembers of itself is a `CopyLink` (team, project, this copy's id, its person, head, epoch, the changes waiting, the journal's last entry taken in). `session-cloud.ts` moves to the base, written against these alone.
- **The desktop's store is the folder** (`@elabora/node` `cloud/projects` `folderCopy`): `cloud-project.json` (a `ProjectLink` is a `CopyLink` with its server and what the room confirmed by hash), the folder's blob store, the hosting's API. `cloudSessionOptions(dir)` gives it with the link and the token. A browser engine will give its own, over the browser's storage.
- `roomUrl` and `blobsOf`, pure, go to `@elabora/core/sync/copy`.

Nothing changes for the desktop app: the same file is written, the same requests reach the API, the copy's machine is the same code.

Weighed:
- **A package of its own** (`@elabora/session`). Rejected for now: every checkout and the app's build would link one more package, for files that are the engine's anyway; the folder and its own check give the same boundary.
- **The copy in `@elabora/core/sync`.** Rejected: the core keeps no timers past a call, and the copy reconnects, waits and throttles.
- **The store's reads asynchronous.** Rejected: the copy reads what was confirmed once, as it starts, from a link its host already holds; a host whose storage is asynchronous loads it before opening, as it loads the link.

*Revisit if:* the base needs a dependency `@elabora/engine` does not have, or another program than an engine runs it.
