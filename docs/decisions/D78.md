# D78. Authors: a person by a stable id and a name, an agent by the person who launched it (12 Nov 2026)

On one computer, the journal's author said what wrote a change (`human`, `agent` with its client's name, `external`, `system`): one person per project, so undo and the history needed no more. In a project in the cloud ([D73](D73.md)) several people write, each with agents of their own, and ⌘Z must take back the asker's work only ([D79](D79.md)).

Decided:
- **`Author` gains `id` and `by`** ([operations](../architecture/operations.md)): `id` is a person's stable id (their account), with `name` to show; an agent's (or a file edit's, `external`) `by` is the id of the person who launched it. Locally both are absent: there is one person, and every agent is theirs.
- **Who sets them.** A copy in the cloud writes them on the changes it sends (its person, and that person as the `by` of its agents and file edits); the server sets them again from the connection that sent the change, never trusting a copy's word, since the rule of rebase ([D74](D74.md)) depends on the author's kind.
- `belongsTo(author, person)` (`@elabora/core` `ops/batch.ts`) is the one rule of « mine »: a person's own changes, and the work of agents they launched; an agent's own changes for an agent. Locally, system changes (a migration, the agents' rules brought up to date) are the person's too; in a project in the cloud they are no one's. The lock a build writes is never a step.

*Revisit if:* an agent is launched for a team rather than a person (a connector shared by an organisation).
