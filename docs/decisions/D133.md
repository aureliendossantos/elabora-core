# D133. The miniatures' renders are four requests of the session's base, the canvas service's (21 Nov 2026)

A browser draws the editor's miniatures in frames of the canvas page given a frozen render (D130). The desktop's host pushes its renders to its hidden pages (`thumbPush`, `momentPush`, `blockPreviewPush`, `measurePush`, in the app's engine host); a browser's engine has no hidden page and must give the render back.

Decided:
- **Four requests of the protocol**, `thumbRender { screen, language? }`, `momentRender { screen, at }`, `blockPreviewRender { args }` and `measureRender { screen, language }`, as `ThumbRequests` of `@elabora/player/thumbs-protocol` types them. Each answers `SceneRender`: an id, the render frozen at the view asked (`screenRenderOf`: its files by path, kind and hash), the course's reference size (slides at `presentation.fit.reference`, 1600 × 900 by default; a scrolling course 1280 × 720) and a version, the SHA-256 of the render (its stylesheets by their hash) and the size; a miniature has no bars, so of the outline its version keeps where the screen is (the sections' and screens' ids), not the titles: a screen renamed draws only its own miniature again. The measure, drawn with the player's bars, keeps the titles. `blockPreviewRender` adds `block` (the id of the block added, `''` for a layout, a backdrop or a screen style, whose version ends with `:layout`) and `slides`. An unknown screen is `not-found`.
- **In the session's base** (`packages/engine/src/base/thumbs.ts`, `SessionThumbs`), so that both sessions answer them and the conformance suite plays them against both. A screen and a moment come from the session's renderer (its memo, its contexts with the texts marked, so a measure has its fields); a block's preview renders the project as `add_block` (or `update_screen` for a layout, a backdrop, a style) would leave it, from the files in memory, nothing written.
- **The canvas service's** (D102): a session without it answers them not here.
- **The files a render names are declared first**: the browser's session adds them to what its relay serves the canvas host (D105, the review's third lock), as the canvas's own renders do. The desktop's session declares nothing: its canvas host serves the module's files itself.
- **The desktop does not change**: its pushes stay in its host, with their own version (which also hashes the player's sources on the disk); these requests are new beside them. A browser's page draws with the player it was built with, so the version needs no player's hash there.

*Revisit if:* the desktop's miniatures come to be drawn from these renders too (then one version for both), or a preview of a block costs too much on a large course (its render context made once per state of the project, as the desktop's host keeps it).
