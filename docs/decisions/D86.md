# D86. A project's validation kept change by change, in the core (12 Nov 2026)

A project's room validates every change it places, and refuses one after which the project has an error it did not have ([D73](D73.md)). It validated the whole project each time: in Node, about 190 ms for a module of 200 screens on a loaded computer (144 ms on a quiet one), 600 ms of a Worker's time, so one or two changes a second for everyone in the project. The desktop engine already validated only what a change can affect, in place, in its session.

Decided:
- **The core keeps a validation as a value** (`@elabora/core/validate/incremental`): `validationState(files)` validates the whole project and keeps what the checks found per screen and per project check; `revalidate(previous, files)` gives the next one, running again only what the files changed can affect, and never changes the previous one. A server keeps the value of its head and computes the next one for a change it may still refuse. `newErrors(before, after)` is the room's rule: the errors, counted by code, file and path, whose count grew.
- **What runs again**, as the engine's session did (its logic moves to the core, the engine uses it): a screen file changed, its screen checks, those of the screens that mention an id whose element was added, removed or changed in it, and the project checks that read screens; an asset, the screens that mention it and every project check; a file no check reads (a translation), every project check; anything else (`course.json`, the plan, a component, the theme), or a project in another format, everything. What changed is found by comparing the two snapshots, not by trusting a list.
- **The same findings as a whole validation.** A validated text whose maths fail is reported once in a run however many screens show it; screens checked apart report it once, as the whole run does. A test compares the value kept with a whole validation after every change the convergence bench places and after edits of every example that reach other screens (an id of another screen, a block other screens name, a plan item, an asset, a validated text on two screens, course.json); with the neighbouring screens, the project checks that read screens, or the once-only maths left out, it fails (the bench alone does not see the neighbouring screens: the examples do). 300 draws of the bench passed.

Measured in Node on the founder's computer while another test run used it (`scripts/validation-measure.ts`, medians, before and after in turn):

| | whole validation | kept | after a wake |
|---|---|---|---|
| 7 screens, a block's text | 13 ms | 3.9 ms | 16 ms |
| 7 screens, course.json's title | 11 ms | 12 ms | 23 ms |
| 200 screens, a block's text | 190 ms | 20 ms | 224 ms |
| 200 screens, course.json's title | 248 ms | 272 ms | 522 ms |

A change to screens only, the most frequent, costs a tenth; `acceptChange` with it, 23 ms at 200 screens. Of the 47 commands by name ([D84](D84.md)), those that write only screens take that path: a screen's settings, blocks (added, changed, moved, duplicated, converted, placed), layers, events, narration lines and timings, continuity, dialogue nodes. Those that write `course.json`, the plan or `elabora.lock.json` still validate everything: creating, deleting, moving and duplicating a screen (its sections), `rename`, the course's settings, the player, variables, findings ignored, a speaker removed, every command of the plan, and `replace_text` when it reaches `course.json`. A translation runs the project checks only. After a wake (a room's memory is lost), the first change pays a whole validation of the head as well.

Weighed:
- **Results by file kept by the hash of its content**, the checks across files run again. Rejected: the screen checks read the course, the plan and other screens; which inputs each reads is what the engine's rules already say, tested.
- **Each check saying what it reads** (to run only those a `course.json` field reaches). Left for later: 34 checks to annotate, for changes that are rarer.

*Revisit if:* changes to `course.json`, the plan or `elabora.lock.json` (creating, deleting, moving or duplicating screens, renaming, the course's settings, the plan) become frequent in rooms: today an agent's batch is validated once and these are rare for a person, so they keep the price of a whole validation; or a project check that reads screens (tracking, the player) grows past a few milliseconds.
